## Orientation

This design covers ordin, a Rust and Tauri desktop application for business users. From revision 0.9.0 ordin is framed as an **exo-harness**: it sits on top of a replaceable vendor harness (Claude first, then GitHub Copilot) and adds a coordinating agent and services — memory, a credential-brokering sandbox, ArtCraft and the APM marketplace — that reach every harness through MCP (ADR-036 to ADR-039). Revision 0.10.0 adds shell and JavaScript to the sandbox, a white-label interface, internationalisation from the start, on-device dictation, sign-in performed by each harness itself, and approval hooks written once in Rust for every harness (ADR-040 to ADR-045). From revision 0.8.0 the person talks to **Ordin**, a coordinating agent bundled with the application, which delegates to the installed agents, forms and coordinates crews, and shows each screen as blocks from a fixed catalogue (ADR-027, ADR-028). Workspaces link documents where they live — SharePoint, Confluence, git repositories and local folders — and every change pushed back is approved (ADR-029). Memory is the memory component (`memory/`) and agent-written code runs in the sandbox (`sandbox/`), both embedded (ADR-030, ADR-031). Revision 0.10.9 makes code a first-class kind of work in a workspace: ordin coordinates agents on code alongside the engineer's own IDE, each coding task works in its own git worktree, and the language servers serve agents and change review (ADR-052 to ADR-054). Revision 0.11.0 makes **workflows** first-class: Ordin coordinates a new crew as it goes, a saved workflow repeats its steps, and each workflow opens as a screen where it can be changed, duplicated, exported as a file and imported (ADR-064). Revision 0.12.0 makes workflows fully capable — branches, loops and workflows that run other workflows, in the same outline, with a diagram to read — and shares them through GitHub and GitLab repositories (ADR-065, ADR-066). Revision 0.18.0 adds the **ordin server**: the same core running headless on a remote Linux server as one person's ordin, reached through a chat channel, Telegram first (ADR-073). Revision 0.19.0 lets the person's chat and the company's NATS events start its runs through triggers; nothing starts from a clock (ADR-074). Revision 0.20.0 makes Telegram a service to agents through the MCP Front, with every post approved (ADR-075). Revision 0.21.0 keeps the server running all the time and adds Slack as a chat channel beside Telegram (ADR-076). Revision 0.22.0 brings the Telegram tools to the desktop where Telegram is installed, and limits dictation to macOS's own on-device recognition (ADR-077, ADR-078). Revision 0.25.0 absorbs crucible's agent machinery, rewritten in Rust in the one build: agents come from catalogue repositories on GitHub in crucible's format, APM packages are imported, a person makes an agent with the agent maker while ordin writes, checks and rehearses it in fixed code, and publishing is a pull request the company reviews and merges on GitHub (ADR-081 to ADR-085). Revision 0.27.0 lets agents come from several **agent repositories**, named by IT or added by the person, and reads and writes agents in the ordin format and the APM format through format plug-ins compiled into the build (ADR-086, ADR-087). Revision 0.29.0 maps each agent catalogue component to the crucible code it carries, has Ordin turn a request into requirements before the library is matched, and runs drafting on the person's own harness (ADR-088). Revision 0.37.0 lets people who look after an agent repository curate its catalogue (ADR-091). Revision 0.38.0 makes **handovers** between people first-class: lifecycles, read from crucible's journeys, say who comes next and what the work must hold, and a handover carries one person's results and a note to the next person through a Git repository or SharePoint folder they both use (ADR-092). Revision 0.39.0 shows what every agent is made of and lets anyone read each part (ADR-093), and imports, checks and fixes agents and parts, including Claude Code and Copilot set-ups, and builds parts of every kind for the library (ADR-094). Revision 0.40.0 starts a workspace for a lifecycle stage in one step, gives lifecycles their own draft, and makes the inspection screens show only what is needed, with the rest on demand (ADR-095). Revision 0.42.0 makes ordin a modular monolith whose screens use the backend only through one Service API, and lets the person's desktop show their own ordin servers beside its own work, through each server's REST API with Server-Sent Events, reached directly over HTTPS (ADR-096). Revision 0.43.0 gives the ordin server two profiles, one person's own ordin or one hosted agent with an identity of its own, and makes ordin the replacement for wrightrun, so one build runs the desktop, the personal server and hosted agents from one machine to a scaled Kubernetes deployment (ADR-097, ADR-098). Revision 0.50.0 brings Slack into working together: handovers are announced in Slack as the person, a lifecycle stage can name a Slack channel, a link opens the handover in the receiver's ordin, and Ordin reads the Slack channels a workspace links and answers under the person's approval or a narrow rule they set once (ADR-102). Revision 0.51.0 lets a team build up shared knowledge with no server: a workspace in Team Knowledge mode shares all its memory facts and knowledge pages through a folder in a GitHub or GitLab repository, one plain file per item, sent after one card and taken back into each person's own ordin, with no Git knowledge needed (ADR-103). Revision 0.52.0 lets knowledge pages link to each other, with the pages that link to each page shown on it, other names and tags, suggested links the person accepts, and renames that keep links working, and makes a workspace's knowledge folder safe to open and edit in another Markdown app (ADR-104). Revision 0.53.0 states that repeating work on a timetable is started by a standard scheduler outside ordin, sending NATS events to triggers on the person's ordin server, with ordin as the runtime (ADR-105). Revision 0.54.0 makes a Jira project a third handover place, where the handover travels on one Jira issue assigned to the next person, with its record kept as the issue's comments, and lets a workspace link Jira issues as read-only items, reached with an API token the person makes or the company's Atlassian app (ADR-106). Revision 0.55.0 makes whatever must happen on every run of a hosted agent ordin's own fixed code, switched on in configuration and never left to the model: a content check through a checker the organisation supplies, configured context steps before the model, any model provider reached by declared settings with no provider named in ordin, and fuller Slack support for an agent that answers in team channels (ADR-107). Revision 0.56.0 brings the UI prototype up to revisions 0.50.0 to 0.54.0, with scenes for Slack, team knowledge, knowledge page links and Jira (12 — UI prototype). Revision 0.57.0 lets the person continue an earlier conversation with Ordin, putting the current one away as **Clear** does, and switch between a workspace's conversations from a picker in the conversation panel (ADR-108). Revision 0.58.0 tells Ordin the person's interface language and lets the person change it in words, and lets people make a language with Ordin's draft, edit any language's wording, and export and import language files, with the approval wording checked by the person before a drafted or imported language is used (ADR-109). Revision 0.59.0 lets a Team Knowledge workspace read any number of other teams' folders beside the one it shares to, read-only, with each item's folder named for agents and small folders ranked fairly beside large ones; a person may adopt one item into their own team's folder as a recorded copy, and a company may name folders every applicable workspace reads (ADR-110). Revision 0.60.0 makes agentic memory a core capability: every agent session with memory rules remembers through the one memory under one model, a fact carries the things it is about and the links between them, recall follows those links one step, Ordin writes summaries with the facts they came from, knowledge pages name the things they explain, and the person sees and governs all of it — things, links, history, fading, what each answer used and what each run remembered (ADR-111). Revision 0.61.0 makes ordin's knowledge wiki a bundle of the Open Knowledge Format, which ordin writes and reads at version 0.2, so any tool that reads the format reads ordin's pages and ordin reads other teams' bundles and glossaries (ADR-112), and adds **knowledge agents**: ordin in the agent profile reads Git repositories into the same memory graph and answers retrieval questions, a team's workspace asks one knowledge agent as its front door, which asks other knowledge agents in parallel within deadlines and returns one merged, ranked, sourced answer, with no model call and no Git fetch while a person waits; only knowledge agents answer, a desktop only asks, and outside tools can search them over a read-only MCP endpoint (ADR-113). From revision 0.62.0 ordin **ships in increments** planned in the release roadmap, each build composing only the modules its build switches turn on and showing nothing of the rest, and **updates itself from one signed release feed**: the desktop downloads a newer version in the background and installs it when the person restarts or quits, a personal server replaces itself when the person asks, and hosted agents are updated by their operators (ADR-114). Revision 0.63.0 makes knowledge inherit its readers: a knowledge agent shows a person a fact only if the system holding its document — GitHub, GitLab, Confluence or SharePoint — would let that person open it when they ask, checked at the source for the few documents behind the answer, with no copy of reader lists, every doubt withholding, and the person's accounts linked from the sign-ins their own ordin already holds; knowledge agents also read Confluence spaces and SharePoint libraries (ADR-115).

Its main purpose is to let people who are not technical use agents: the application performs every technical step itself, configured by a signed organisation profile that IT publishes (ADR-012, ADR-013). It:

- installs AgentWright agent packages from the company's internal APM marketplace through the `apm` CLI; *from revision 0.25.0, adds agents from the company's catalogue repositories, makes new ones with the person and publishes them for review on GitHub (ADR-081 to ADR-085);*
- runs them as local sessions on a vendor harness the person has signed in to in its own way: their installed Claude Code first, then Copilot (ADR-038, ADR-044);
- lets a coordinator agent direct crews of local and remote agents, within guardrails enforced in fixed code;
- organises work in workspaces, each gathering its folders, linked Confluence locations, agents, crews, conversations and history, and publishes local documents to Confluence through linked folders;
- gives the person friendly access to their files, and creates and edits files of many kinds through the ArtCraft apps, which agents reach through each app's MCP mode (ADR-039);
- supports software engineering in an engineering mode: projects, code editors with language plug-ins (Go, Rust, Java, TypeScript first), review of agent changes, git, an engineer-only terminal, and GitHub work through `gh` with approval set by the engineer;
- reaches agents deployed in wrightrun through the runtime's caller interface, or through Slack, posting as the person in a dedicated channel and reading the replies from the thread. *From revision 0.43.0 these are hosted ordin agents (ADR-098).*

The clickable prototype [`user-interface.html`](./user-interface.html) is part of this design: it shows every pattern of 11 — UX guidelines on screen, and 12 — UI prototype says how `/spec` reads it and lists where it and the text still disagree.

It is written for the people who will review it and run `/spec` on it. The neighbouring designs are the builder's (`ff-dossier-to-agent-builder/docs/design/builder-v2/`) and wrightrun's (`agent-wright-runtime/docs/design/agent-runtime/`). This design depends on both and changes neither. The next move is `/spec ordin-desktop`. The confirmation spike on driving the person's installed Claude Code with the ordin hook (C-19, C-25, C-26) ran on January 2026: the Claude halves passed, with sessions started with `--restricted` in place of `--safe-mode` (revision 0.28.0). C-61 ran on January 2026: a restricted session reads nothing from the agent folder, so the Claude Code Installer's output reaches the session through `--append-system-prompt-file` and `--plugin-dir` (revision 0.48.0). `/spec ordin-desktop` Phases 1 and 2 are written (`docs/spec/ordin-desktop/`); revision 0.48.0 carries their approved edits, ADR-100 and ADR-101. `/spec ordin-desktop` Phase 3 (72 component specs) is written; revision 0.49.0 carries its approved edits (decision 80): dependency edges, module-owned interfaces only a program implements (ADR-100 amendment), the libraries the specs name, and the interface names they fix. `/spec ordin-desktop` Phases 4 to 6 are written (14 cross-cutting specs, the Generation Playbook, the self-audit); revision 0.49.1 carries their approved edits (decision 81): the glossary terms the specs use, the cross-cutting policies they fix, and the build commands.
