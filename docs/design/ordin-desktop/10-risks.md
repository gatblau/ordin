## Assumptions

| ID | Area | Assumption | Rationale |
|---|---|---|---|
| A-01 | Platforms | The first release ships for macOS and Windows; Linux is later. | Business users' desktops; confirm with OQ-7. |
| A-02 | Distribution | Updates come from a company-hosted, signed update feed through Tauri's updater. | Controlled updates. *Amended in revision 0.62.0 (ADR-114): the feed is the release feed the project publishes; a company may host its own and name it in a branded build or a verified profile.* |
| A-03 | Performance | 150 ms p95 for interface actions that call no model; under 3 s to an interactive start. | Concrete targets in place of "rich and simple"; to be revised after the prototype. |
| A-04 | Scale | Up to 8 concurrent local sessions. | Each session runs a CLI server; memory per server is unmeasured (R-05). |
| A-05 | Crews | Guardrail defaults and ceilings as stated in 07 — Cross-cutting. | They mirror the builder's bounded loops (5 rounds, 60 minutes for run-until-check) with headroom for coordination. |
| A-06 | Security | Shell commands run only for system-changing packages, each approved unless a declared rule allows it. | Business-user default; packages with document-only authority never need a shell. |
| A-07 | Security | The journal relies on operating-system disk encryption, not its own. | Company-managed laptops have disk encryption; to confirm. |
| A-08 | Retention | Journal records, conversations and history are kept for 90 days by default; the person enters another whole number of days, at least 1, in Settings › History (decision 57). Pending approvals and in-progress runs are never pruned. | Long enough for support, short enough to limit stored content. |
| A-09 | Retention | Logs rotate and are kept for 14 days. | Support diagnostics. |
| A-10 | Observability | The application sends no telemetry and exports no metrics or traces in the first release. | Single-user tool; privacy first. |
| A-11 | Runtime | One Copilot CLI server per local session, with the agent folder as its working folder. | Isolation of instructions, skills and permissions between agents; to confirm against the SDK's multi-session support (C-03). |
| A-12 | Identity | OIDC sign-in uses the authorisation-code flow with PKCE in the system browser. | Standard for desktop public clients. |
| A-13 | Crews | The person builds crews in a guided crew builder: purpose, agents and limits within the profile's ceilings. Charters can be exported and imported as files to share, but are never edited by hand; they are not distributed through the marketplace in the first release. | Smallest step that keeps crews non-technical (ADR-012); see OQ-8. |
| A-14 | Package reviewer | *Withdrawn in revision 0.2.0* (ADR-013): IT decides trust through the organisation-recommended executable set. | The person cannot be asked a security judgement (ADR-012). |
| A-16 | Updates | Agent updates within the same major version are applied automatically between runs. Other updates are offered in plain language with what changed. Application updates install on restart. *Amended in revision 0.36.0: what decides is what the agent may do or read, not its version number. An update that does not change what the agent may do or read is applied between runs without a question, and the agent's line says "Updated between runs today; what it may do hasn't changed, so nothing was asked." An update that changes what it may do or read asks the person first (11 — UX guidelines §5.2).* | No technical step for the person (ADR-012); a major version may change behaviour, so the person chooses. *Amended in revision 0.36.0: a version number does not show whether what the agent may do has changed, so ordin compares that instead.* |
| A-17 | Sign-in | Only the GitHub sign-in is asked on first start. Sign-ins to the identity provider and Slack are asked the first time a remote agent needs them. | Fewest steps before the first result (R-10). |
| A-18 | Files | Previews cover images, PDF and text natively, and other kinds through the platform's own preview where one exists. | No editor of the application's own (non-goal). *Amended in revision 0.36.0 (ADR-048, ADR-057, ADR-070): by hand the person edits Markdown documents (with a formatting toolbar), knowledge pages, agents' own memory pages (with the same toolbar from 0.36.1) and email drafts (with the same toolbar); everything else is changed by agents or opened in its own app (00 — Overview, non-goals; 11 — UX guidelines §5.6).* |
| A-19 | Files | File versions are kept for the journal's retention period, with the latest always kept, and are capped at 10 GB per installation, oldest first. | Bounded disk use on business laptops. |
| A-20 | ArtCraft | Apps are fetched on demand when a person or an agent first needs one, not at installation. | Small installer; thirteen apps would be large. |
| A-21 | Files | A place holds up to 100,000 files and 20 folder levels. The Files view shows its first rows within 300 ms of opening a folder, and search returns first results within 1 s, at the 95th percentile. | Concrete limits for "large number of files" (decision 11); typical shared-drive folders. |
| A-22 | Files | Search across a workspace uses a local index of file names, and of the text of documents the application can read, kept current by watching the workspace's places. | Searching 100,000 files by reading them on demand is too slow (A-21). |
| A-23 | Workspaces | *Superseded in revision 0.8.0 by ADR-029: a workspace links content where it lives, and a loose dropped file is linked from where it was dropped from.* Files dropped loose into a workspace are copied into a folder the application creates under the person's Documents, named after the workspace; dropped folders are added as places, not copied. | People keep their own folders (ADR-015); loose files need a home they can find outside ordin. |
| A-24 | Ordin | Ordin's block calls and crew-tool calls fit within one Copilot request per conversational turn for at least 90% of turns, so routing through Ordin does not double the request cost of a single-agent task. | Ordin adds a model turn in front of every delegation; its cost must stay small against the subscription allowance (OQ-3). |
| A-25 | Pushes | A workspace's origins report a version or change time for each file and page (SharePoint drive items, Confluence page versions, git commits), so the core can detect that the origin changed since it was read. | ADR-029 refuses to push over a newer origin version. |
| A-26 | Dictation | The bundled speech model (Windows, and macOS before 26) is downloaded from the update feed on first use of dictation, not carried in the installer. | Keeps the installer small; dictation is optional (ADR-043). *Withdrawn in revision 0.22.0 (ADR-078).* |
| A-28 | Knowledge | A workspace holds up to 500 knowledge pages of up to 3,000 words each, in a `knowledge/` folder inside the workspace's own folder; search returns matching pages with the documents, within A-21's 1 s. | Concrete limits for ADR-057; one piece of work rarely needs more pages than that. |
| A-27 | Branding | A run-layer brand pack may rename the coordinator; Ordin's package takes the display name as a setting. | White-labelling covers what the person meets most (ADR-041). |
| A-30 | Usage | ordin's net use of a plan, compared with doing the same work in the harness alone, is measured in the pilot from the journal's counters, not assumed; the level table in ADR-062 is a starting point to be tuned from those counts. | Ordin adds coordinator turns and saves turns elsewhere; only measurement says which wins for real work (ADR-062). |
| A-31 | Voice | Tone, register, length and the person's notes, given once in Ordin's fixed instructions, are enough for Ordin to follow them in at least 9 of 10 messages; the application's fold keeps length within the limit in every case. | Rewriting each message in the application would cost a second model call (ADR-063). |
| A-29 | Run again | The journal keeps each finished run's inputs by name, with where each lives and the version read, but not their content; Run again reads each input from its source and compares versions there. This adds a few references per run, pruned with the journal (A-08). | Lets Run again name a newer version before it starts without keeping a second copy of every input (ADR-060). |
| A-15 | Inputs | Command inputs are free text plus attached files in the first release. Typed forms wait for a builder RFC (OQ-5). | The builder emits commands with arguments, not typed schemas. |
| A-32 | Workflows | A workflow holds at most 20 steps and 8 agents, and a workflow screen draws within 300 ms; a step's line is at most 200 characters. *Revised in revision 0.12.0 (ADR-065): at most 50 steps and blocks, nested at most 4 deep, For each at most 50 items, Repeat until at most 10 times, workflows running others at most 3 levels; the screen and its diagram draw within 300 ms at those sizes.* | Concrete limits for ADR-064; work longer than 20 steps is better split or left to Ordin. |
| A-33 | Workflows | Ordin can condense a crew run's rounds into steps that a person recognises as what happened in at least 9 of 10 runs, checked in the pilot. | **Save as workflow** depends on it; the screen shows the steps before saving, so a poor condensation is seen, not saved silently. |
| A-34 | Reports | A report holds at most 12 parts and 2 MB of data; a table at most 10,000 rows and 30 columns; a chart at most 8 series and 5,000 points; key figures at most 8. A report screen draws within 300 ms and a table scrolls without delay at those sizes. | Concrete limits for ADR-067; bigger data belongs in a spreadsheet, which **Save as…** writes. |
| A-35 | Progress | Agents built by AgentWright state a plan of three to seven steps through the plan tool, and mark them, in at least 9 of 10 tasks of more than one step, checked in the pilot. | ADR-068's steps depend on it; without a plan the screen falls back to events only, so a miss is visible, not misleading. |
| A-36 | Published copies | Fetching the followed branch of each repository holding a Markdown original with published copies, at workspace open, at start and every 15 minutes, stays within GitHub's and GitLab's limits for one person's token, for up to 20 such repositories per person, and finds a merged change within 15 minutes while ordin runs. | ADR-069's automatic updates depend on it; if limits are hit, the interval grows and the original shows when GitHub was last checked, so a delay is visible. |
| A-37 | Email | Checking each workspace's email links at workspace open, at start and every 15 minutes, with Graph's or Gmail's change queries, stays within each service's limits for one person's token, for up to 20 email links per person. | ADR-070's new-email counts depend on it; if limits are hit, the interval grows and the Email group shows when it last checked. |
| A-38 | Email | Checking each linked folder on the company's mail server at workspace open, at start and every 15 minutes, by asking for messages above the last number seen, with one connection at a time per person, stays within the server's connection and rate limits for up to 20 email links per person (ADR-071). | The IMAP adapter's new-email counts depend on it; if the server limits connections, checks are queued and the Email group shows when it last checked. |
| A-39 | Network | Every outbound call — the profile, the update feed, ArtCraft and other downloads, harness and adapter calls — uses the computer's own proxy settings and trusted certificates, including a certificate the company adds to inspect traffic. | Locked-down company networks reach the internet only through their proxy (ADR-072). *From revision 0.22.0 one exception: the ordin server's NATS connection, because `async-nats` has no HTTP proxy support (C-53); NATS is reached directly (A-41).* |
| A-40 | Chat channel | The organisation profile lists the chat channels a company allows for the ordin server. Telegram is off unless the profile allows it; with no profile, the server owner chooses (ADR-073; decision 41). | The company's data-protection review of each chat service. |
| A-41 | Events | The company's NATS servers are reachable from the ordin server over an outbound TLS connection, and the subjects worth starting runs from carry JSON payloads (ADR-074). | Read the company's subjects and their payloads before the first trigger; binary payloads wait for OQ-40. |
| A-42 | Agent repositories | An agent repository holds at most 2,000 parts, and ordin reads at most 10 agent repositories per person. At those sizes **Used by** for one part answers from the local index within 200 ms, and the health report of one repository is computed within 10 s after a fetch, in the background. | The catalogue view (ADR-091) depends on it; frozen crucible's own catalogue holds 516 files. | A-43 | Handovers | Finding handovers through GitHub's review requests labelled `ordin-handover`, at start, at workspace open and every 15 minutes, stays within GitHub's limits for one person's token, for up to 50 open handovers a person is asked to review (ADR-092). | The search is one call per check; the label narrows it to ordin's pull requests. |
| A-44 | Handovers | SharePoint refuses a write to `handover.yaml` made against an older version of the file, so two installations appending at once never lose an event; the second retries from the file as it now reads (ADR-092, R-83). | Graph supports conditional writes with the file's version; C-69 confirms it for the handover folder. |
| A-45 | Agent repositories | **What it's made of** for one agent, at most 200 parts in its closure, is drawn from the local index within 300 ms, and **Read it** renders a part of at most 100 KB within 200 ms (ADR-093). | The closure is the one the Resolver already computes when an agent is added; the index holds every part's text. |
| A-46 | Remote screens | On the company network, a Remote API command that does not wait for a model answers within 150 ms at the 95th percentile, and an event reaches the desktop's screens within 500 ms of the server's journal recording it, with JSON bodies (ADR-096). | HTTP/2 keeps one connection per server for commands and the event stream; the server does the work and sends only what the screens draw. ## Risks

- **R-01 — Packages behave differently outside VS Code.** If the CLI does not load what APM deploys, or a package depends on editor state, migrated workflows change behaviour. *From revision 0.25.0 read "what the Installers write" for "what APM deploys" (ADR-082; C-60, C-61).* *Response:* spike C-01 before the prototype, and compatibility tests per package.
- **R-02 — A tool request escapes the rules engine.** If any tool path skips the permission handler, policy is not enforced. *Response:* spike C-02, keep the tool allowlist minimal per instance, and treat OS sandboxing as the fallback (OQ-11).
- **R-03 — The declaration format changes under us.** wrightrun's spec set is Draft with a failed audit, and builder RFC 35 is Draft. *Response:* pin the spec revision in the conformance suite; ship with "declaration not enforced" reporting for unknown format versions.
- **R-04 — Crews consume users' Copilot allowance quickly.** Each round costs coordinator and member requests. *Response:* request budgets per charter, visible counters and conservative defaults (A-05); OQ-3.
- **R-05 — Memory and CPU with many CLI servers.** *Response:* measure in the prototype; lower A-04 if needed.
- **R-06 — Slack app approval is refused or delayed** by workspace administrators, which blocks the Slack route. *Response:* the HTTP route covers wrightrun agents that expose it; request approval early. *Amended in revision 0.50.0 (ADR-102): the same refusal blocks the Slack Service's notices and linked channels; every Slack notice then falls back to email, and the person may connect their own Slack app where the Slack workspace lets members install apps.*
- **R-07 — Prompt injection through documents or remote replies** steers an agent into external actions. *Response:* fixed-code policy, approvals for externally visible actions, and crew members limited by charter.
- **R-08 — Unknown outcome of an external action after a crash** leads to duplicates if retried. *Response:* action keys in the journal; never resend automatically; show the person.
- **R-09 — wrightrun is late.** Remote members depend on a runtime with no code yet. *Response:* local crews ship first; the remote adapters follow wrightrun's first release.
- **R-10 — Sign-in friction across three accounts** (GitHub, OIDC, Slack) erodes the adoption benefit. *Response:* one sign-in on first start (A-17); the others only when a remote agent is first used; measure onboarding abandonment.
- **R-11 — No organisation profile, or an incomplete one.** Without it the application cannot set itself up without technical steps (ADR-013). *Response:* the profile is a prerequisite of the pilot; the Setup Assistant names the missing setting to IT in the help request.
- **R-13 — The GitHub token needs broad access.** APM's documentation names the `repo` scope, which for a classic token also allows writing. *Response:* prefer a company-owned GitHub App with read-only repository access (OQ-6, C-06); the token never leaves the keychain except into the environment of one `apm` call. *From revision 0.25.0 there are no `apm` calls (ADR-082); the token is used for cloning and fetching agent repositories and, through `gh`, for publishing pull requests (ADR-084).*
- **R-14 — ArtCraft apps are immature.** Three are early alpha and ten in development (getartcraft.com/apps, January 2026); PhotoCraft's author calls it "not yet a Photoshop replacement for daily professional work". *Response:* pin versions in the profile, approve app by app after a test of the pilot's file kinds, keep every prior version of a file, and fall back to the system's default app for hand edits (OQ-17).
- **R-15 — No CLI for a platform.** The app pages read list a CLI download for macOS only. *Response:* confirm per app (C-07); where no CLI exists, agents get no Craft tool for that kind and the start-up report says so.
- **R-16 — An agent damages a person's file.** *Response:* versions of every change, writes only to granted places at the granted access, and moves to the bin instead of deletion (ADR-015).
- **R-17 — The office editors are not ready when the pilot starts.** WordCraft, GridCraft and DeckCraft are in development, and the user chose to wait (ADR-018). *Response:* choose pilot workflows whose formats pass C-09 at the time, PDF through PdfCraft first, and keep the pilot date tied to ArtCraft milestones.
- **R-18 — Engineering mode widens what runs on the computer.** Language servers, check commands and git remotes are programs and network access beyond the business features. *Response:* enabled only by profile, with check commands through the Rules Engine and language servers pinned by APM or the profile (*from revision 0.25.0 by the profile only, ADR-082*); OQ-18 decides the terminal.
- **R-19 — An agent changes a shared repository without a person's decision.** This happens when an engineer switches approval off for a write kind (ADR-023). *Response:* writes need approval by default, the profile ceiling can forbid switching some kinds off (OQ-22), every operation is journalled and shown, and the engineer can switch approval back on at any time.
- **R-20 — Language servers need toolchains.** Java's server needs a Java runtime, and the Go and Rust servers work best with their toolchains. *Response:* each plug-in declares what it needs, and the Setup Assistant installs it or reports it plainly.
- **R-21 — A draft is published to Confluence by accident** through a linked folder. *Response:* the link is approved once with the audience stated; new, renamed and removed files wait in *Ready to publish* for the person's check; only updates to already-published files go automatically; every push is journalled with a link to the page (ADR-026).
- **R-22 — Publishing changes a document's layout.** Converting a document to a Confluence page can lose formatting. *Response:* only text documents become pages; every other kind is attached as the exact file; Word files stay attachments until conversion is settled (OQ-24).
- **R-23 — Workspace search falls behind on very large places.** *Response:* the index is built in the background with its progress shown as a count; until it is complete, search says how much is indexed (A-21, A-22).
- **R-24 — Ordin is a single point of quality.** Every request passes through Ordin, so a weak delegation or a wrong summary affects all work. *Response:* acceptance checks for Ordin's package covering delegation, crew forming and plain-language summaries; the person can always talk to one agent directly (11 — UX guidelines §5.12); the journal keeps each member's own output beside Ordin's summary.
- **R-25 — Word and PowerPoint cannot be changed in the first pilot.** Ordin's document updates depend on WordCraft's and DeckCraft's command-line tools (ADR-018, C-13). *Response:* Ordin reads and summarises those files and changes Markdown and Confluence pages; for Word and PowerPoint it states plainly that it cannot change them yet.
- **R-26 — Agent code in other languages cannot run.** The sandbox runs Python, shell scripts and JavaScript (ADR-040); native programs (compilers, build tools) cannot run in it. *Response:* agent packages are told what the sandbox runs; Ordin reports a request that needs a native program as not possible in the sandbox; project checks stay outside under the engineer's approval (OQ-26).
- **R-28 — Local models make the application heavier.** Bundled embedding and reranking models add to the installer and use processor time while memory is built. *Response:* small models chosen in `/spec` with size and latency limits; memory work runs in the background at low priority.
- **R-27 — A document steers Ordin.** Linked documents from SharePoint, Confluence and repositories are read by Ordin and crew members, and may carry injected instructions. *Response:* Ordin has no action tools of its own (ADR-027); every push and every externally visible action needs the person's approval on a card the application builds (ADR-028, ADR-029); recall's write gate treats content as data (ADR-030); knowledge pages are written only by Ordin and the person, and agents read them as reference only (ADR-057).
- **R-29 — Crews use up people's own plans.** Sessions run on each person's own Claude or Copilot plan (ADR-044), so a busy crew can reach the plan's limits and stop mid-task. *Response:* budgets per charter counted in turns and tool calls (OQ-3), conservative concurrency defaults, and a plain message when the harness reports a limit; the organisation-paid route is the fallback.
- **R-31 — Crews reach a plan's limits sooner.** Sessions started by ordin are the person's own Claude Code sessions, as several terminal sessions would be; all count against the person's one plan, which the person pays for (user, January 2026). Anthropic permits an end user to sign in to the unmodified Claude Code binary with their own subscription, and states that plan limits assume ordinary, individual usage (code.claude.com/docs/en/legal-and-compliance, read on January 2026), so a busy crew reaches the plan's limits sooner. *Response:* ordin never handles the credential and never modifies the binary (ADR-044); budgets and concurrency defaults per charter (R-29); a plain message when the harness reports a limit; the organisation-paid route (OQ-28 options a to c) stays available.
- **R-32 — Shell scripts written for full bash fail in the sandbox.** The sandbox's shell is a subset, with no native programs. *Response:* errors return to the agent with the unsupported feature named; packages are told the subset; the toolbox grows by need (ADR-040).
- **R-33 — Dictation is poor in some languages or on older machines.** *Response:* recogniser coverage per locale checked before the pilot (C-24); the microphone is hidden with a plain reason where no local recogniser covers the locale; typing always works. *From revision 0.22.0 (ADR-078) only `SpeechTranscriber`'s locales on macOS 26 and later apply; elsewhere dictation is off.*
- **R-34 — Untranslated or clipped text in a locale.** *Response:* a missing catalogue entry fails the build; pseudo-locale and right-to-left screen tests on every build; reviewed translations per locale (ADR-042).
- **R-35 — A published copy looks different from its original.** Word, PDF and slides made from Markdown can lose layout the readers expect. *Response:* copies are made by the apps that own each format (ADR-048); the approval card names the app; a person can open each copy before approving; tables and headings are part of the pilot's conversion check (C-28).
- **R-36 — GitHub and GitLab behave differently.** Pull and merge requests, branch protection and approvals differ, so the same operation kind can mean different things. *Response:* the GitLab tool maps each operation kind explicitly and is covered by the same shared scenarios as the GitHub tool; an operation with no exact match is refused, not guessed.
- **R-37 — Parallel coding tasks load the computer.** Each open task has a checkout, a language-server instance and a build cache, and attempts multiply token use. *Response:* attempts only when the person asks, capped by the profile (default 3); attempts count against the crew budget; a task's language server stops when the task is idle; worktrees are removed when the task is settled.
- **R-39 — A knowledge page is wrong or out of date, and is relied on.** A summary can misread a source, or a source can change after the page was written; keeping pages current also uses tokens on the person's plan. *Response:* each page cites its sources with the version read; a page whose source changed says "may be out of date" and is re-checked before Ordin relies on it; updates are shown to the person before they are used; a figure sent back to an origin is taken from its source, never from a page; Ordin writes pages only when work finishes (ADR-057).
- **R-40 — Searching every workspace tempts copying content between them.** Seeing another workspace's documents beside this one's makes it easy to paste or reuse them where the access was not granted. *Response:* results across workspaces are shown to the person only, never to an agent (ADR-059); agents keep searching only their own workspace through the MCP Front; using a document in another workspace means adding it there with the Add flow, at the access granted there.
- **R-41 — The catch-up becomes noise in busy workspaces.** A workspace with many documents and runs could show a long note on every return, and the person learns to ignore it. *Response:* from revision 0.23.0 nothing is written into the conversation on return; changed documents are marked in the tree, with counts on folded folders, and the rest is on Home (ADR-079). *Residual:* in a folder where many documents change, many marks show; the filter *Changed since you looked* lists them in one place.
- **R-42 — Run again silently uses a changed input.** A document can change between runs, so the same task gives a different result without the person knowing why. *Response:* the journal keeps the version each input was read at (A-29); the form names each newer version before Start; nothing starts until the person presses the form's button or Start (ADR-060).
- **R-44 — A cheaper model gives a worse result.** *Response:* the level table keeps writing, code and crew planning on *Standard* or above under *Balanced*; a step that fails its check is tried once on the next level; every result offers **Try again with a more capable model**; the pilot tunes the table (A-30).
- **R-45 — A reused answer is out of date.** *Response:* reuse needs an exact match over the same input versions, expires after 7 days, is labelled with when it was made, offers **Ask again**, and never covers an action.
- **R-47 — Notes for Ordin are used to give it instructions.** A person, or someone with their computer, writes notes such as "never ask before sending". *Response:* notes are limited to 300 characters and given to Ordin as style preferences only; approvals, sending and access are decided by the application's own code, which notes cannot reach (G4, ADR-010); the plain-language rules come first in Ordin's instructions.
- **R-46 — Trimming drops a detail the agent needed.** *Response:* every trimmed result carries a reference to read the rest; the setting can be turned off; the conversation itself is never compressed word by word (ADR-049, ADR-062).
- **R-48 — A workflow file carries instructions meant to mislead an agent.** A file from someone else can word a step to steer the agent doing it. *Response:* import is checked in fixed code and opens *not saved yet* with every step shown in full; a file grants no access, adds no agent and raises no limit; step lines reach agents as data inside each agent's declared rules; every push, post and publish still needs the person's approval (ADR-064).
- **R-49 — Saved steps go stale.** An agent is updated or removed, or a document the steps rely on changes shape, and the saved steps no longer fit. *Response:* the crew plan checks the workflow's agents and versions before Start; Ordin takes over when a step fails twice or a check finds a shortfall, says so, and offers **Update the workflow…** (ADR-064).
- **R-50 — People edit away a check that mattered.** Removing *Ordin checks the result* or *Asks you first* makes a run quicker but less careful. *Response:* each change is a version with **Restore**; the approval the application requires before anything leaves the computer cannot be removed by a workflow (ADR-064).
- **R-51 — A loop multiplies the cost of a run.** A For each over many items, or a Repeat until whose condition Ordin decides, can use many turns. *Response:* every loop has a maximum within the company's; the estimate before Start counts loops at their maximum and each Ordin decision; the crew's limits on rounds and time cover every repeated step (ADR-065, ADR-062).
- **R-52 — A colleague's change to a shared workflow alters what runs.** *Response:* a newer version in the repository is shown with what changed and used only when the person chooses; runs record the version used; the check runs on every version; branch protection and reviews in the repository decide who may change it (ADR-066).
- **R-53 — A chart makes a wrong number look authoritative.** An agent's miscalculation drawn as a clean chart is believed more readily than a paragraph. *Response:* every part names where its numbers come from and which agent worked them out; **Show as table** shows the rows; Ordin's *checks the result* applies to reports as to any result; numbers from company systems come through the sandbox's broker, with the time of the read (ADR-067).
- **R-54 — An agent marks steps done that it did not do.** *Response:* a step marked done with no activity seen says so; the events seen during each step are one click away; the run's result is still checked by Ordin before it is reported done (ADR-036, ADR-068).
- **R-55 — A merged mistake reaches the copies' readers without a second look.** With *keep copies up to date*, a wrong change merged on GitHub is in SharePoint and Confluence within 15 minutes. *Response:* only changes that reached the original's origin update copies, so the repository's own review applies; changes by Ordin and agents always wait for approval; every update is journalled with its commit, listed on the original and on Home; SharePoint and Confluence keep the copy's previous version; **Stop keeping up to date** is one click (ADR-069).
- **R-56 — Copies fall behind when no one who published them runs ordin.** ordin has no server, so copies update only while an installation that published them is running. *Response:* every copy carries a line naming its original and when it was last updated, so readers can see it is stale and where to look; Home reports updates made at start; a team that needs updates at every merge can run a publishing job beside ordin (ADR-069, alternatives).

- **R-65 — Text in an event steers an agent.** A NATS event's fields reach agents as inputs, and a crafted field could carry instructions. *Response:* filters in fixed code with no model turn; only mapped fields, at most 4,000 characters each, reach the run; event content is data (01 — trust boundary 4); every external action still needs the person's approval; subjects limited to the profile's list (ADR-074).
- **R-66 — A linked Telegram group steers an agent, or its members' data spreads.** Anyone in a linked group can write text agents will read, and the server keeps their messages. *Response:* messages are content, never instructions; posts only from approval cards; nothing in a linked chat acts as a command; only linked chats kept, deleted with the link; profile can list allowed chats (ADR-075).
- **R-67 — A server that never stops fails quietly.** A hang, an expired sign-in or a lost channel could leave ordin running but useless for days. *Response:* the watchdog and supervisor, sign-in checks every 6 hours with a warning before expiry, channel outages reported on the other channel, and a restart message to the person (ADR-076). *From revision 0.22.0 Claude Code reports no expiry, so there is no warning before it: the sign-in is checked every 6 hours and before each harness session, and its end is reported at once (ADR-076 note).*
- **R-68 — A person mishandles the desktop bot's key.** Connecting Telegram on the desktop has a business user copy a secret key from BotFather; pasted somewhere else, such as a chat, it lets someone else read and post as the bot. *Response:* the key is pasted only into ordin's own screen, which says "Never paste it into a chat" and stores it in the keychain; **Remove Telegram** deletes it; the person can make a new key in BotFather, which stops the old one working; IT can connect the bot instead (ADR-077, decision 47). *Accepted by the user, January 2026 (decision 47).*

- **R-38 — An accepted change no longer fits the engineer's working copy.** The engineer kept working, in ordin or their IDE, while the task ran. *Response:* the change is applied with a three-way merge; a conflict shows both versions and is never forced (§5.11).

- **R-110 — Earlier installations do not take a profile that names team knowledge folders.** *Added in revision 0.59.0 (ADR-110).* The profile's types refuse unknown keys, so an installation before revision 0.59.0 keeps its last verified profile when `team_knowledge` appears. *Response:* nothing breaks on those installations; the administrator guidance says to add the key once installations have updated.
- **R-111 — An adopted copy goes out of date unnoticed.** *Added in revision 0.59.0 (ADR-110).* Only an installation that reads the source folder raises the "changed at its source" mark. *Response:* the copy says where it came from wherever it is recalled, and the adoption record carries the source's version so a reader of both folders can compare.
- **R-112 — Decay never lets a fact go.** *Added in revision 0.60.0 (ADR-111).* The memory component's salience heuristic gives every fact at least 0.45, above the 0.3 floor below which decay may end a fact, so fading facts are shown but none is ended by time. *Response:* "Fading" is shown as a sign of disuse with **Keep**, and is not described anywhere as a countdown to deletion; a change to the salience heuristic is a later decision of the memory design.
- **R-113 — Forgetting one fact also forgets summaries the person wanted.** *Added in revision 0.60.0 (ADR-111).* A summary made from a forgotten fact is deleted with it, because it may restate that fact. *Response:* the **Forget** confirmation names how many summaries go with it; Ordin may write a new summary from the facts that remain at the end of a later run.
- **R-114 — Wrong things and links mislead recall.** *Added in revision 0.60.0 (ADR-111).* An agent may name the same thing two ways or state a link that is not true, and link expansion then brings in facts about the wrong things. *Response:* near-identical names and kinds are merged on write; links carry the agent's confidence and are one ranked signal among several, after the reranker; the person sees every thing and link, can make two things one, and can correct or forget a link; **What Ordin used** shows which links an answer relied on.
- **R-115 — Link expansion slows recall on a large workspace.** *Added in revision 0.60.0 (ADR-111).* Each step out multiplies the facts considered. *Response:* one step by default, at most 32 linked things a step and 200 candidates in all; measured by C-93; with team folders read, the soft limit of A-58 still applies.
- **R-116 — Text from documents or other agents steers a front door or a desktop.** *Added in revision 0.61.0 (ADR-113).* A fact, a name, a link word or a table of contents could carry an instruction. *Response:* no model on a question's path at any knowledge agent; everything from documents and other agents is data; the reply is written on the person's own ordin under its usual rules and approvals; the acceptance test plants "ignore previous instructions" in a document.
- **R-117 — A wrong audience exposes content.** *Added in revision 0.61.0 (ADR-113).* An operator states that a whole audience may read a repository when some members may not, and those members receive its facts. *Response:* the check refuses a repository without the statement; the start-up report lists each repository beside the audience; caches are per access group; per-person checks are the later decision that removes the risk.
- **R-118 — A stale cached answer is served.** *Added in revision 0.61.0 (ADR-113).* A change notice is lost and a front door serves an answer that relied on an old commit. *Response:* every cached answer records the commits it relied on; a broken change stream is opened again at once, and until it is, the front door checks the commits in the proxy's table of contents before serving; C-96 measures the 10 s target.
- **R-119 — Slow proxies make answers partial.** *Added in revision 0.61.0 (ADR-113).* A proxy that is slow or down leaves its knowledge out of the first result. *Response:* the result names what did not answer in time and when each source was last fetched; **More found** carries late results until 5 s; a backup proxy covering the same repositories is asked after 300 ms; a hot copy removes a frequent hop.
- **R-120 — Glossary conflicts are left unsettled.** *Added in revision 0.61.0 (ADR-113).* Two glossaries give one other name to different things and nobody settles it, so the first listed wins indefinitely. *Response:* the agent's status names each conflict and both glossaries; settling it is a change in Git by the glossaries' owners; no automatic settling.
- **R-121 — Reading large repositories costs too much.** *Added in revision 0.61.0 (ADR-113).* One model turn per changed document, billed to the organisation key, can grow with repository size. *Response:* pages and Open Knowledge Format concepts are read with no model call; unchanged documents are not read again; a daily budget with documents left unread reported (A-67); C-98 measures cost per document.
- **R-122 — The Open Knowledge Format changes before 1.0.** *Added in revision 0.61.0 (ADR-112).* Version 0.2 may change in ways that make ordin's files or reading out of date. *Response:* ordin writes 0.2 and reads what 0.2 tells readers to accept; unknown keys and types are kept, never errors; a new major version is read only after a decision to adopt it.
- **R-123 — A scaled knowledge agent runs two memory instances over one store.** *Added in revision 0.61.0 (ADR-113).* The `requests` and `runs` roles each construct a Memory Service over the one PostgreSQL store, which the memory component has not confirmed is safe (its RISK-014). *Response:* knowledge agents run in the single shape first; the scaled shape waits for the memory component's answer (decision of the user, January 2026).
- **R-124 — The update key is lost or leaked.** *Added in revision 0.62.0 (ADR-114).* A lost key leaves every installation unable to accept an update, so each must be reinstalled by hand; a leaked key lets someone sign a false update that installations would accept. *Response:* the private half is a file on the maintainer's own computer, outside version control and never given to a CI service, with a backup copy the maintainer keeps (recorded January 2026); a leak is answered by a release signed with the old key that carries a new public key, and by withdrawing the feed until it is published. *Downgrade:* Tauri's signature covers the installer, not the version the feed claims, so a feed naming an older signed installer as newer would install it on a desktop; the desktop logs a warning at start when its running version is lower than the last version it started, and the server compares the archive's own `--version` with the offer before replacing anything.
- **R-125 — A server self-update stops half-way.** *Added in revision 0.62.0 (ADR-114).* A failed download, unpack or replacement, or a restart systemd does not carry out, could leave a personal server on neither version. *Response:* the archive is verified before anything is replaced; each program is replaced by rename with the current one kept as `.previous`; a failed replacement keeps the running version and can be tried again; the restart uses the normal stop order, and a server that does not come back is restarted by its unit (C-100). When systemd does not carry out the restart, both programs are restored from their `.previous` copies, so the running server never starts a hook of another version, and the update can be tried again.
- **R-126 — A delegated SharePoint token is misused on the agent.** *Added in revision 0.63.0 (ADR-115).* The exchanged token could read anything the person can open while it lives. *Response:* it is used only for `GET` of item identifiers through Graph `$batch`, held in memory for one question, never stored, logged or passed to a proxy; a test checks the datastore, logs and metrics.
- **R-127 — Access checks push answers past one second.** *Added in revision 0.63.0 (ADR-115).* *Response:* checks run in parallel with the proxy fan-out, staged (ten first), batched, within 300 ms; late ones go to **More found** (C-105). A result holding facts a proxy checked for one person is not saved, so questions answered from proxies' per-person sources always miss the cache; a front door that asks often about such a source takes a hot copy, which removes the hop.
- **R-128 — Source systems limit the agent's requests.** *Added in revision 0.63.0 (ADR-115).* *Response:* Git is checked per repository, not per file; the 60-second memory and batching bound requests; a limited system's facts are withheld as unchecked, never shown unchecked.
- **R-129 — An account is linked to the wrong person.** *Added in revision 0.63.0 (ADR-115).* *Response:* the account is taken from the system's own answer to the presented sign-in, never from a name the desktop states; a later link from another account replaces the earlier one.
- **R-130 — Removed access is still honoured for a short time.** *Added in revision 0.63.0 (ADR-115).* With no notice from the system, a person removed by an owner may still see that knowledge for up to the remember period. *Response:* 60 seconds by default; **Check on every question** for sensitive sources; GitHub and GitLab notices end it at once.
- **R-131 — A Confluence restriction added without a page edit is seen late.** *Added in revision 0.63.0 (ADR-115).* With per-person checks off, a view restriction added to a page without editing it leaves that page's facts visible to the audience until the next fetch reads the restriction (15 minutes by default). *Response:* each fetch re-reads the restrictions of every page it holds facts for, and retires the facts of a page that became restricted; operators of spaces where this matters turn on per-person checks or shorten the fetch interval.
- **R-132 — The agent's SharePoint sign-in goes stale.** *Added in revision 0.63.0 (ADR-115).* Microsoft may return a new refresh token on each use; the copy the operator placed in the agent's secret store then ages, and in the scaled shape another instance may hold an older one. *Response:* reading runs on one instance per firing (the built-in duty); the reader keeps the newest token in its process and uses the stored one only at start; when Microsoft refuses it, SharePoint reading stops, the knowledge status says "Sign in to SharePoint again", and `ordin-server knowledge sign-in sharepoint` makes a new one (C-107).

## Alternatives considered

- **wrightrun as the local managed harness.** Rejected for the first release: no Copilot subscription route, PostgreSQL and Python in the installer, and the work folder in a database instead of local files (ADR-002). *Moot from revision 0.43.0: ordin replaces wrightrun (ADR-098).*
- **Desktop client for wrightrun only (no local sessions).** Rejected: the user requires local sessions and crews that are mostly desktop-based, and local documents are the desktop's main advantage.
- **Keep VS Code with Copilot as the front end.** Rejected: it is the friction ordin sets out to remove.
- **A hosted web application.** Rejected for now: local documents and the person's own Copilot subscription favour the desktop; compare again if most work moves to shared systems.

## Rollout and Rollback

*Amended in revision 0.62.0 (ADR-114): ordin ships in increments, each installable and complete for the journeys it carries, reaching existing installations through the release feed. Which steps and build switches each increment carries is planned in the release roadmap (kept by the maintainers outside the repository) over the Generation Playbook's dependency order, not in this design. The steps below remain the order of proof inside them.*

Rollout follows these steps:

1. **Compatibility proof.** Run one valuable AgentWright package through the person's installed Claude Code outside an editor, with the ordin hook and the MCP Front, and settle C-19, C-20, C-22, C-25 and C-26; then the same package through the Copilot route, settling C-01 to C-03, C-05 and C-27 (ADR-038, ADR-044, ADR-045).
2. **Desktop prototype.**
   - Organisation profile and the first-start sequence of the Setup Assistant.
   - Catalogue and *Add an agent* from the internal marketplace. *From revision 0.25.0 from the agent repositories, through the agent catalogue port's first phase, use (ADR-081, ADR-082, R-69).*
   - One local agent end to end (golden path).
   - Files view with places, and PdfCraft for the person and as Craft tools; WordCraft, GridCraft and DeckCraft added as each passes C-09 (ADR-018).
   - Engineering mode: one project, the code editor, change review and git for one language.
   - Approvals and the journal.
3. **Crews and the remote route.**
   - Local crews with a coordinator.
   - Then wrightrun members over HTTP and through Slack, once a wrightrun deployment exists. *From revision 0.43.0 (ADR-098): hosted ordin agents in place of wrightrun.*
   - *From revision 0.43.0 (ADR-097, ADR-098):* the agent profile in the single shape, with Slack, the caller interface and the full Rules Engine, after C-74 and C-77 to C-81 are checked; then the scaled shape on Kubernetes with PostgreSQL, the Run Queue and the Duty Timer; then the operator screens on the desktop (UX-A67).
   - *From revision 0.61.0 (ADR-112, ADR-113):* the Open Knowledge Format page changes on the desktop first, with no knowledge agent; then one knowledge agent in the single shape as a front door with no proxies; then a front door with proxies, after C-95 and C-96 are measured. A knowledge agent in the scaled shape follows only once the memory component confirms that more than one instance may share one store (its RISK-014; R-123; settled by the user, January 2026).
4. **Reliability and distribution.**
   - *From revision 0.42.0 (ADR-096):* the Service API on Tauri's IPC from the first desktop build; then the Remote API and the Server Connector, once C-71 is checked.
   - Signed installers and the update feed.
   - Recovery after restart.
   - Support export.
5. **Business-user pilot.** Compare against the VS Code experience on the same tasks, measuring each expected benefit as follows. The benefits are hypotheses for the pilot to test.

   | Expected benefit | Measure |
   |---|---|
   | Easier adoption | First successful task rate; onboarding abandonment |
   | Less technical training | Training time; support requests per active user |
   | Better task execution | Accepted-result rate; corrections per result |
   | Approvals people understand | Approval time; mistaken approvals and cancellations |
   | Existing agents reused | Share of workflows moved across with no change in behaviour |
   | Better operational control | Failed runs recovered; duplicated external actions |
   | More predictable cost | Cost per accepted result; budget overruns |
   | Knowledge and memory people can see | How often sources are inspected; how often memory is corrected |

**Rollback.**
- Updates come from a company feed, so a bad release is withdrawn by re-publishing the previous version. *Amended in revision 0.62.0 (ADR-114): updates come from the release feed, the project's or a company's; installations accept only a newer version, so a bad release is withdrawn from the feed and replaced by a newer one that undoes it; installations that already took it keep running it until then, and a personal server's previous programs are kept as `.previous` after a self-update.*
- The journal schema only moves forward, and a backup is copied before each migration. Rolling back the application restores that backup, and records written by the newer version are lost.
- Packages roll back through APM: install the earlier version into a new instance. *From revision 0.25.0 there is no APM install (ADR-082): an earlier version is the one an earlier lock file names, with repository, commit and digest per part, and it is built and installed into a new instance through the Resolver and Compiler and the Installer; the exact steps are fixed in `/spec`.*
- Crew charters are versioned. A run records the charter version it used.
