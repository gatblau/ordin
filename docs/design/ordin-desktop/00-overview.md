## Summary

ordin is an **exo-harness**: it sits on top of a vendor's agent harness and adds what that harness lacks (ADR-036). The vendor harness runs the inner loop of an agent session: model calls, the tool loop and the context. ordin runs the outer loop: which agents do the job, with what authority, memory and credentials, and whether the job was done. Two things make up that outer loop:

1. **A coordinating entity.** **Ordin**, a coordinating agent that ships with the application, mediates between the person and the one or many agents that do a job, at all times, so that the job is done as well as it can be.
2. **Services the vendor harness does not provide.** Agentic memory; a sandbox for agent-written Python, shell and JavaScript that brokers the person's corporate credentials (ADR-040); the ArtCraft apps; and the internal APM marketplace, through which agents are found, installed and managed. *Amended in revision 0.36.0 (ADR-082, ADR-083, ADR-086): agents now come from agent repositories, named in the organisation profile or added by the person, and ordin also makes agents with the person through the agent maker; the APM marketplace is no longer how agents are installed (G2, G40).* Every service reaches the harness through MCP (ADR-037), so the same services serve every harness. The guardrails, approvals and journal are enforced in ordin's own fixed code, outside the harness.

The vendor harness is replaceable. Claude is the first harness, and GitHub Copilot follows (ADR-038).

The person opens the application and talks to Ordin. Ordin knows every installed agent, delegates each request to the right one or forms a crew, answers the agents' first questions itself, and explains what matters in plain, brief terms. The screens are assembled by Ordin, for the task at hand, from a fixed set of trusted blocks (ADR-027, ADR-028).

Under Ordin, the application installs AgentWright agent packages from the company's internal APM marketplace (*amended in revision 0.36.0 (ADR-082, ADR-086): from agent repositories, in the ordin format or the APM format*), runs them as local agent sessions on the vendor harness, and lets several sessions work together as a **crew**. Ordin directs each crew within guardrails that the application enforces in fixed code.

From revision 0.10.0 the interface is white-label (ADR-041), internationalised from the first release (ADR-042) and takes dictation through on-device speech services (ADR-043). Each vendor harness signs the person in its own way, and ordin attaches to it (ADR-044); approvals are enforced by ordin's own Rust hook, shared by every harness (ADR-045).

*Revision 0.9.0 note.* Sections written before ADR-036 to ADR-039 name the Copilot SDK and Copilot CLI as the local harness. Read them as describing the Copilot adapter; the Claude adapter comes first, under the same rules (ADR-038).

A crew can also include agents that already run in the wrightrun runtime. The application reaches those through the runtime's caller interface, or through Slack, where it posts as the person in a dedicated channel and reads the agent's replies from the thread.

The rules each package declares are enforced by a Rust rules engine. It is written to give the same outcome as wrightrun's on the same scenarios.

*Revision 0.43.0 note (ADR-097, ADR-098).* ordin replaces wrightrun, so one build is required. The ordin server runs either as one person's own ordin (the **personal profile**) or as one **hosted agent** with an identity of its own, serving the people the organisation allows (the **agent profile**). The agent profile provides everything wrightrun's design states, from one machine up to a scaled deployment on Kubernetes with PostgreSQL. Agents described above as running in wrightrun are hosted ordin agents from this revision, and the rules engine is the only one.

Out of scope: building agents, running wrightrun on the desktop, scheduled unattended work, and serving agents to other people. *Amended in revision 0.36.0 (ADR-082, ADR-083, ADR-086): building agents is no longer out of scope; the non-goal was withdrawn in revision 0.25.0, and ordin makes and publishes agents (G40).* *Amended in revision 0.43.0 (ADR-097, ADR-098): running wrightrun is moot, because ordin replaces it; scheduled unattended work and serving other people are in scope for an ordin server in the agent profile, and stay out of scope for the desktop and the personal profile.*

**Six ideas carry the design** (revision 0.36.3, user decision of January 2026; the fourth added in 0.36.4, the fifth in 0.37.2, the sixth in 0.38.0). They are how the project describes itself, starting with the repository README; each one traces to decisions already made.

- **Business first.** Enabling people who are not technical is the application's main purpose (decision 5, G10, ADR-012). The default reader of every screen is the business user (11 — UX guidelines §1); technical detail appears only in a workspace that links a code repository (ADR-050).
- **Agent first.** Agents do the work; the person directs, checks and approves it. Ordin mediates between the person and every agent, checks each result before reporting it done, and assembles the screens for the task at hand (ADR-027, ADR-028, ADR-036; G16, G17; P0).
- **Documents, email and chat are first-class** (user statement of January 2026: "document, email, and chat integration is first citizen"). They are services of ordin itself, reached by every harness through the MCP Front, and no plug-in is needed. Documents are linked where they live and every change goes back to its origin only after the person approves it (G18, ADR-029, ADR-079); Markdown is a native format whose published copies follow it (G32, ADR-048, ADR-069); email is read, filed and drafted with sending approved message by message (G33, ADR-070, ADR-071); chat reaches remote agents through Slack (G5, ADR-008, ADR-009), lets agents read and draft for Telegram (G37, G39, ADR-075, ADR-077), and carries the ordin server's conversation (G35, G36, G38, ADR-073, ADR-074, ADR-076).
- **Making and managing agents.** ordin makes agents as well as running them: the agent maker drafts with the person, ordin writes, checks and rehearses the draft in fixed code, and publishing is a pull request whose merge is the publication (ADR-081, ADR-083 to ADR-085, G40). Git agent repositories are the registry, searched through a local index and pinned by lock files; no registry server is run (ADR-081, ADR-082, ADR-084, ADR-086, ADR-087, ADR-090; R-71). ordin manages those repositories' structure, the structure of each agent and the taxonomy of parts (G41). *Amended in revision 0.37.0 (ADR-091): people who can open a review in an agent repository also curate its catalogue in ordin: they change one part on its own, retire and withdraw parts with their replacements, keep the vocabularies and writing guides, and see which agents use each part and how healthy the catalogue is; every change is a pull request.*
- **An agentic workspace for code.** Code is first-class work beside the company's documents: each coding task in its own copy on its own branch, several attempts compared, every change through change review, language servers serving agents and review (ADR-052 to ADR-054). ordin works alongside the engineer's own IDE and is not an IDE: ADR-052 rejected "ordin as a full IDE", so the project does not describe itself as one.
- **Work passes between people.** A person's results are the next person's inputs. Lifecycles, read from crucible's journeys, say who comes next and what the work must hold; a handover carries the results and a note through a place both people already share, is checked in fixed code before it leaves, and is accepted or sent back with a reason. Each installation stays one person's (ADR-092, G42).

## Motivation

AgentWright packages today run inside a coding host (VS Code with Copilot or Claude Code), or on the wrightrun server once it exists. The coding host asks a business user to understand a workspace, an extension, a chat panel, slash commands and file trees before the first useful result. That is the friction ordin sets out to remove.

Three needs are not met by either existing route:

1. **A business-user front end on the person's own machine.** It works with local documents and has no terminal and no IDE. The wrightrun design rules out a user interface of its own and reaches people only through a chat system (`agent-wright-runtime/docs/design/agent-runtime/00-overview.md`, non-goals; ADR-024 there).
2. **Several agents working together for one purpose.** Both the builder and wrightrun list crews of several built agents as a non-goal (`ff-dossier-to-agent-builder/docs/design/builder-v2/00-overview.md:60`; `agent-wright-runtime/docs/design/agent-runtime/00-overview.md:56`). Something has to own crews, and that is this application.
3. **Use of the subscription people already hold.** Most users hold GitHub Copilot seats. The Copilot SDK runs on that subscription through a GitHub sign-in. Anthropic does not allow third-party products to offer claude.ai login without prior approval, so a Claude route would need an organisation API key in any case (*Decision record*, item 4).

Doing nothing leaves every business user either in VS Code or limited to a single agent in Slack. Neither route gives them crews.

Enabling people who are not technical is the application's main purpose (decision 5 below). Each technical step left to the person — installing a tool, approving a hook, typing an address, reading an error from a command-line tool — recreates the friction the application exists to remove.

## Goals

- **G1.** A business user completes a task with an installed AgentWright package and inspects the result, without opening a terminal, an IDE or a configuration file.
- **G2.** The application installs, updates and removes AgentWright packages from the company's internal APM marketplace by driving the `apm` command-line tool. A package's executable parts (hooks, MCP servers, bundled programs) are enabled only when the organisation's trust policy covers them. The business user is never asked to judge them (ADR-013). *From revision 0.25.0 (ADR-082) agents come from the catalogue repositories the profile names, in crucible's format, checked and built by ordin itself; APM packages are imported, and `apm` is no longer bundled. From revision 0.27.0 they come from several agent repositories, named in the profile or added by the person (ADR-086), in the ordin format or the APM format, read and written by format plug-ins (ADR-087).*
- **G3.** The application runs several local agent sessions at once, each isolated in an agent folder of its own.
- **G4.** A crew is Ordin, as coordinator, plus member agents, working towards one stated purpose. The coordinator chooses each next step. *Amended in revision 0.36.0 (ADR-064, ADR-065): a crew that runs a saved workflow follows the workflow's steps, with no coordinator turn per round; its conditions are decided by the application, by Ordin from words, or by the person, and Ordin takes over only when the steps do not fit (G28).* Guardrails are enforced by the application's own code with no model call in the decision: the members allowed, the hand-offs allowed, the round, time and request budgets, the approval points and the kill switch.
- **G5.** A crew member, or a direct conversation, can be an agent deployed in wrightrun. It is reached through the runtime's caller interface, or through Slack, where the application posts as the person in a dedicated channel and reads replies from the thread. *Amended in revision 0.43.0 (ADR-098): the agent is a hosted ordin agent, reached through its caller interface by the Hosted Agent Adapter, or through Slack.*
- **G6.** Local sessions run on a vendor harness the organisation profile names: Claude first, then GitHub Copilot (ADR-038). Each harness signs the person in through its own flow, on the person's own subscription, and ordin attaches to the signed-in harness (ADR-044). The application never asks for, reads or stores a model credential, and holds no shared secret of the organisation.
- **G7.** For local sessions, the rules a package declares in `wrightrun-declaration.yaml` are enforced in fixed code. On every scenario the two share, the outcome equals wrightrun's. *Superseded in revision 0.43.0 (ADR-098): there is one Rules Engine, with wrightrun's semantics in full, for every profile.*
- **G8.** Every action that is externally visible or destructive is shown before it happens: what it is, where it goes and what it affects. The person approves or rejects it. Every run, approval and result is recorded in a journal that survives a restart, and a resumed run never repeats an external action that already completed.
- **G10.** A business user never performs, configures or judges a technical step. A workspace that links a code repository (G13) is the one place where technical detail is shown (ADR-019, ADR-050, ADR-052). That means no command line, configuration file, server address, channel name, package internals or security decision about hooks, MCP servers or programs. Their only actions are signing in with accounts they already have, choosing what they want done, supplying inputs and approving consequences stated in plain language. The application performs every technical step itself: installing and updating tools and packages, checking them, connecting accounts, registering remote agents and recovering from failures. When it cannot finish a step, it says in plain language what happened and what the person can do, and offers to send the details to IT (ADR-012, ADR-013).
- **G11.** The person reaches their files in a friendly way. They see named places (Documents, Desktop, a project folder they chose), not paths. They add a folder with the system's own folder picker, and drag files in and out. Every file has a preview, its versions, where it came from (which run or person), and actions: *open*, *edit*, *give to an agent* and *save a copy elsewhere*. Removing a file moves it to the system's bin. Agents reach only the places the person has given them (ADR-015). *Amended in revision 0.36.0 (ADR-079, UX-A52): a document opens on its own short document page, with what it is, its state and two actions at a glance (**Open in [app]** and **Ask Ordin about this**), and its versions and where it lives on request. A file that is not Markdown shows no preview and no edit action there; it opens in its own app (11 — UX guidelines §5.6).*
- **G12.** The person and the agents create and change files of many kinds through the ArtCraft Crafting Apps: images, vector illustrations, video, photos, PDFs, page layouts, interface designs, documents, audio, slides, drawings and spreadsheets. Agents reach the apps through each app's MCP mode, fronted by the application (ADR-039). The person opens a file in the matching app's window with one action. The application installs, pins and updates the apps itself, as the organisation profile approves them; the person never installs one (ADR-016, ADR-017).
- **G13.** Code is a first-class kind of work in a workspace, not an exception mode: ordin coordinates agents' work on code beside the company's documents, alongside the engineer's own IDE (ADR-050, ADR-052). A linked code repository opens as a **project**, with a project tree, search across files, and code editors in tabs *(amended in revision 0.36.0 (ADR-047, ADR-050, UX-A18): there is no project view, project tree or search across files; a linked repository appears as a **Code** group in the workspace's tree, and the code editor, Changes waiting and the terminal open as screens in the centre)* with syntax highlighting and language intelligence. Every change an agent proposes appears in a change review, where the person accepts or rejects each change. Git status, history, branches and commits are shown. The engineer has a terminal of their own that agents cannot use. GitHub work — pull requests, issues, reviews, workflow runs — goes through the GitHub CLI (`gh`), which the application installs and signs in. Agents may use it, with the engineer choosing which kinds of GitHub operation need their approval. Language intelligence comes from language-server plug-ins, first for Go, Rust, Java and TypeScript, which the engineer chooses among, turns off and configures in Settings within the company's list; the editor highlights every language it knows, with or without a server (ADR-055), and edits code with the server's completion; the Go server is gopls and the Rust server is rust-analyzer (ADR-056). Software-engineering agents (AgentWright packages with system-changing authority) work on a project under the same rules, approvals and check commands as any other agent. Any text file, in a project or not, opens in the code editor (ADR-019 to ADR-021). Each coding task works in its own copy of the repository on its own branch, so several agents can work at once and the engineer can compare attempts and keep one (ADR-053). Agents and change review use the language servers: agents to find their way through the code, change review to show the new problems each change brings (ADR-054).
- **G14.** Work is organised in **workspaces**. A workspace is a named home for one piece of work ("Q3 supplier review"). It gathers the places that work uses, its linked Confluence locations, the agents and crews allowed in it with their access, and its conversations, approvals, results and history. The person creates a workspace by giving it a name, drags files and folders into it, and switches between workspaces. Agents and crews started in a workspace reach only that workspace's places and Confluence links, at the access granted there. Files and folders view at scale: a folder tree, a sortable list, search across the workspace and a breadcrumb trail, for places of up to 100,000 files and 20 folder levels (A-21) (ADR-025).
- **G15.** People and agents use **Confluence** content. They browse and read Confluence pages, and pages can be given to agents as inputs. Local documents are published to Confluence: text documents become pages, every other kind of file is attached to a page as the exact file. A folder linked to a Confluence location publishes on its own after the person approves the link once; updates to already-published files are pushed automatically, and new or removed files wait in a list for the person's quick check. An edit made in Confluence is shown, and the person can bring a copy back; it never overwrites a local file. The person signs in to Confluence with their own account; the site comes from the organisation profile (ADR-026).
- **G16.** The person's main interface is one conversation with **Ordin** per workspace. Ordin knows each installed agent's commands, skills, arguments, lifecycle and rules, delegates each request to one agent or forms a crew and coordinates it, answers the members' first questions itself, and checks each result against the request before reporting it done (ADR-036), and passes on only what needs the person, in plain and brief language with a recommendation. A crew Ordin forms can be kept and reused on request (ADR-027).
- **G17.** Screens fit the task instead of the person learning screens. Apart from the workspace switcher, the conversation, the *Needs you* list, Settings and engineering mode, everything the person sees is a block Ordin shows from a fixed catalogue, rendered by the application's own code. Approval cards are built by the application, never by an agent (ADR-028). *From revision 0.10.13 Home and the search box are fixed parts too, built by the application's own code (ADR-058, ADR-059).*
- **G18.** A workspace links documents where they live — SharePoint (typically Word and PowerPoint), Confluence, git repositories on the computer (typically Markdown kept on GitHub) and local folders. The person asks Ordin to add them; the application reads and shows them; Ordin has agents change them through the Craft tools; and each push back to the origin is approved by the person, grouped per request, after a check that the origin has not changed meanwhile (ADR-029).
- **G19.** Ordin remembers across sessions — the person's preferences, earlier decisions and what it has learned about their documents — through the memory component (`memory/`) embedded in the application. Crew members share that memory within a workspace, and the person can see, correct and delete what is remembered (ADR-030). Beside memory, each workspace keeps **knowledge pages** that Ordin writes when work finishes: explanations with their sources, marked when a source has changed, read by every agent in the workspace and kept on the computer (ADR-057).
- **G20.** Code that an agent writes — Python, shell scripts or JavaScript — runs only in the sandbox (`sandbox/`), embedded in the application, with no network of its own and no files except those passed in; company systems are reached only through the sandbox's broker (ADR-031, ADR-040).
- **G22.** The interface is white-label: product name, coordinator name, logos, icons, colours, fonts, links and legal text come from a brand pack, set by a branded build and by the organisation profile, while approval cards and safety cues stay fixed (ADR-041).
- **G23.** Every interface text is translatable from the first release: catalogue messages, the person's locale, locale-correct formatting and right-to-left layout; Ordin talks in the person's language (ADR-042).
- **G24.** The person can dictate wherever they can type in the conversation and forms, with speech recognised on the computer: the operating system's on-device service where one exists, and a bundled local model elsewhere (ADR-043). *Amended in revision 0.36.0 (ADR-078): there is no bundled model. Dictation works only where the operating system provides it, macOS 26 and later; on Windows and older macOS the microphone button is hidden and Settings says dictation isn't available.*
- **G25.** A person who works in many workspaces keeps track of them without opening each one. **Home** shows what waits for them, what is running and what finished or changed, across every workspace; documents changed elsewhere are marked in the workspace's tree until the person opens them, and nothing is written into the conversation on return (ADR-079). One search box, **Search or go to…** (Ctrl+K, ⌘K on a Mac), finds across the person's own workspaces for the person only, goes to things and starts actions; agents still search only the workspace they work in. Finished work can be **run again** with its previous inputs, newer versions named before it starts. All four are built by the application's own code, with no model call, and decide nothing. Repeating work on a schedule stays off the desktop: Ordin offers to ask IT to set it up in wrightrun (ADR-058 to ADR-060). *Amended in revision 0.53.0 (ADR-105): the request asks IT to have the company's scheduler send an event that starts a trigger on the person's ordin server, or, without one, for a hosted ordin agent.*
- **G21.** When no installed agent fits a request, Ordin finds one in the internal marketplace and proposes it; it is added on the person's "Add it" (ADR-032). *Amended in revision 0.36.0 (ADR-082, ADR-083, ADR-086): Ordin looks in the agent repositories, not an internal marketplace; when nothing there fits, it says what is covered and offers to make an agent (G40).*
- **G26.** Ordin's coordination costs the person's plan as little as it can. Ordin's own tools are known when ordin is built and kept out of each request, each session is offered only its tools, bulk work runs as code, instructions are assembled in a cacheable order, and simple requests are answered by the application. In Settings, the person makes one choice — *Save my plan*, *Balanced* or *Best results* — with details folded under **More choices**, within the frame the company sets (ADR-062).
- **G27.** Ordin always speaks in plain language and briefly. The person chooses its tone (*Friendly*, *Neutral*, *Warm*, *Direct*), register (*Everyday*, *Formal*), length (*Brief*, *Shortest*), a name to be called and short notes on how they like things explained, in Settings or in words; tone never changes approval cards, errors or facts (ADR-063).
- **G28.** Repeated work repeats the same way. A crew Ordin coordinates as it goes can be saved as a **workflow**: a numbered list of steps, each an agent's one-line job, which may run at the same time as its neighbour, ask the person first or have its result checked by Ordin. A saved workflow runs its steps with no coordinator turn per round, and Ordin takes over only when the steps do not fit, then offers to update the workflow. Workflows are first-class: each opens as a screen in the centre, and can be changed there (every save a version), duplicated, exported as a file and imported from one; an imported file grants nothing and is never run before it is saved (ADR-064). *From revision 0.12.0 (ADR-065) a workflow is an outline of steps and control blocks — If / otherwise, Ask me, For each, Repeat until, Run another workflow — each loop with a maximum, conditions decided by the application, by Ordin from words, or by the person, and a diagram to read it by.*
- **G29.** Workflows are shared where teams already share files: as workflow files in GitHub and GitLab repository folders linked to a workspace, and in a company workflow repository IT names in the organisation profile. Sharing is approved like any send back; a shared workflow says where it lives, shows a newer version before it is used, and never grants access or changes on its own (ADR-066).
- **G30.** Agents show data as **reports**: tables, charts and key figures drawn by the application from data agents send through ordin's MCP server, every number with where it came from. A report can be kept as a **dashboard** and refreshed when the person asks, and saved as a spreadsheet, PDF, slides or document (ADR-067).
- **G31.** Progress reads plainly for anyone: one sentence on what is happening now, a short list of named steps with "step 2 of 4", and what was seen to happen underneath — no percentage bar and no time remaining (ADR-068).
- **G32.** A Markdown document kept in git is the **original** of its published copies — Confluence pages, and Word, PDF and slides files in SharePoint. The copies follow it: a change merged in the repository updates every copy kept up to date, each copy says where its original is, and nothing at a destination is overwritten or deleted without the person's choice (ADR-048, ADR-069).
- **G33.** Agents work with the person's **email**: Ordin and the agents the person allows read the email a workspace links, save attachments and draft replies, through the same ordin interface every harness uses (the MCP Front), and nothing is sent until the person approves the exact message, with recipients outside the company marked (ADR-070). The company's own mail server (IMAP to read, SMTP to send) comes first, Microsoft 365 second and Google Workspace last (ADR-071).
- **G34.** ordin runs entirely in the person's own user account. Installing, starting, updating and repairing ordin, the ArtCraft apps and every other program ordin brings needs no administrator rights, and nothing is placed in areas of the computer a company locks down. Company allow-listing is respected: every program is signed by its publisher so IT can allow it with one rule (ADR-072).
- **G35.** ordin can also run **headless on a remote server**, as one person's own ordin, reached through a chat channel — Telegram first. The person talks to Ordin, receives what needs them and approves from the chat, with the same rules, approvals and hook as on the desktop; the server needs no administrator rights and opens no port (ADR-073). *Amended in revision 0.42.0 (ADR-096): the person's own ordin desktop can also show the server, through the server's Remote API. The API listens on one private address chosen at setup and the desktop reaches it directly over HTTPS; the organisation profile can forbid it, and the server then opens that one port. (Amended in revision 0.47.0, decision 78.)*
- **G36.** On the ordin server, runs start from the person's chat — a message, **/run** with a workflow's name, a file that matches a trigger, **Run again** — and from **NATS events** on subjects the company allows, through triggers the person turns on. Filters are decided in fixed code, events are not lost across a restart where JetStream keeps them, every trigger has limits, and approvals stay with the person. Nothing starts from a clock (ADR-074).
- **G37.** Agents work with **Telegram** as they do with email: Ordin and the agents the person allows read the groups and channels a workspace links, save their files and draft posts, through the MCP Front, and nothing is posted until the person approves the exact post in their own chat with ordin. Posts come from the server's bot; the person's own chat with ordin is never open to agents (ADR-075).
- **G38.** The ordin server runs **all the time**: it starts with the server, is restarted by its supervisor after a crash or hang, keeps every channel connected, and warns the person before a sign-in runs out. It listens to **Telegram and Slack** at once, Slack through Socket Mode with no open port; an approval can be answered on either (ADR-076). *Amended in revision 0.36.0 (ADR-076, decision 50): there is no warning before a sign-in runs out, because Claude Code reports no expiry time. ordin tells the person as soon as the sign-in has ended and asks them to have whoever runs their ordin server sign in again; it never names a technical way in (11 — UX guidelines §5.23).*
- **G39.** *From revision 0.22.0 (ADR-077)* the Telegram tools also work on the desktop when the Telegram app is installed, through a bot of the desktop's own connected on one guided screen; messages arrive while ordin is open.
- **G40.** *From revision 0.25.0 (ADR-081 to ADR-085)* the person makes new agents and publishes them. When nothing in the library covers a request, Ordin says what is covered and offers to make an agent; the agent maker drafts it with the person, and ordin writes it, checks it and rehearses it in fixed code. The person can try it alone, then publish it as a pull request that the company reviews and merges on GitHub. No business user sees a file, a version or a technical choice.
- **G41.** *Added in revision 0.36.5 by the user's statement of January 2026 ("the backend registry is a github repo but its structure and agent structure and taxonomy of combinable parts is the management side ordin can do").* ordin manages agent repositories as well as reading them: the structure of a repository, the structure of each agent, and the taxonomy of combinable parts (the Agent Model's 25 kinds, overlays and vocabularies, ADR-081). What is designed: ingesting a repository into parts with their dependency edges, checking every part and every combination (Checker), composing agents from reused, extended and new parts (ADR-088), borrowed parts and withdrawal with replacement read per part (ADR-090), starting files for an empty repository (ADR-088), and curating the catalogue directly (ADR-091). *Amended in revision 0.37.0 (ADR-091, decision 67): until this revision G41 counted 23 kinds, which was stale (Memory and ControlLoop were added to crucible after the count), and said that curating the catalogue directly (parts on their own, the withdrawn list, the taxonomy) was not designed yet (OQ-54). It is now designed, brought from crucible. Anyone who can open a review in an agent repository curates it on the screen **Parts of [repository]**: one part created or changed on its own, in the kinds crucible's Forge writes (agents stay with the agent maker); parts retired from new agents, replaced and withdrawn, through a withdrawn list whose file format ordin defines; vocabularies, writing guides and which agents each practice fits; the repository's layout and kinds; which agents use each part; and a health report. Every change passes a check of the whole repository and is published as a pull request, reviewed under the repository's own GitHub rules (ADR-084).*
- **G42.** *Added in revision 0.38.0 by the user's statement of January 2026 (decision 68).* Work is **handed over between people** as a first-class item. A person who finishes their part of a lifecycle, such as software delivery, hands their results and a note to the next person, who accepts and starts from them in their own ordin, or sends the work back with a reason. The handover travels through a place both people already share, a Git repository first and SharePoint second; ordin checks in fixed code that the results hold what the next stage needs before they leave, and each installation stays one person's (ADR-092). *Amended in revision 0.40.0 (ADR-095): a workspace for a stage starts in one step, and lifecycles have their own draft.* *Amended in revision 0.54.0 (ADR-106, decision 86): a Jira project on the company's Jira Cloud site is a third place, where the handover travels on one issue assigned to the next person.*
- **G43.** *Added in revision 0.39.0 (decision 69).* Every agent shows **what it is made of**, its parts grouped by kind in plain words, with borrowed parts naming their repository; every part of every kind can be **read**, read-only, by anyone who can read its repository; people who code also see versions, the lock file and the installed files (ADR-093). *Amended in revision 0.40.0 (UX-A64): these screens show name, kind and state first, and the rest on demand.*
- **G44.** *Added in revision 0.39.0 (decision 70).* ordin **imports** whole agents and single parts, from the ordin and APM formats and from Claude Code and Copilot set-ups, **checks** any agent or part on demand, **fixes** what fails, in fixed code where the answer is certain and with the agent maker where it is not, always on a draft, and **builds parts of every kind** a person can write for an agent repository (ADR-094).
- **G45.** *Added in revision 0.42.0 (decision 72).* ordin is **one modular build**: each part of the core is a module that owns its data and is reached only through its service interface, and the screens use the backend only through one **Service API**. The person's desktop is also the **screen for their own ordin servers**: it connects to a server's Remote API, a REST API with Server-Sent Events, and shows that server's workspaces, conversation and *Needs you* beside its own, while the server keeps working when the desktop is closed (ADR-096).
- **G46.** *Added in revision 0.43.0 (decision 73).* The ordin server runs in one of two profiles. In the **personal profile** it is one person's own ordin (G35 to G38, G45). In the **agent profile** it is one **hosted agent** with an identity of its own: an organisation model key, credentials held for each connection, and no person's sign-in. It answers the people and channels the organisation allows, sends approvals to named approvers, keeps memory by channel with direct chats kept apart, and runs the package's recurring duties. A person's desktop reaches a hosted agent by role, through the person's company sign-in: as a caller who asks it questions, as an approver, or as an operator. It never pairs with one as its own server (ADR-097).
- **G47.** *Added in revision 0.43.0 (decision 73).* ordin **replaces wrightrun**: one build provides every capability of wrightrun's design. That covers publishing an agent release, the caller interface, intakes, chat, knowledge sources, settings, the full rules vocabulary, the run queue, recurring duties, operator commands and routes, metrics, traces, retention and erasure, and deployment on one machine or scaled on Kubernetes with PostgreSQL. Packages, configurations and callers written for wrightrun work unchanged, with the exceptions ADR-098 names and reports (ADR-098).
- **G48.** *Added in revision 0.60.0 (decision 91).* **Agentic memory is a core capability of ordin.** Every agent session — Ordin, crew members and agent task sessions alike — remembers, learns and forgets through the one memory, under one model: the kinds of memory (something that happened, something known, a summary), who may write which class, scopes, fading and replacement, and each agent's own memory rules. A fact can carry the things it is about and the links between them, recall finds the things a question names and follows their live links one step, Ordin writes summaries of what it learned with the facts they came from, and the person can see, correct and forget the whole of it, things and links included. ordin desktop, the personal server and the agent profile share the model and differ only in where memory is kept and in its scopes, so a later knowledge agent builds on it unchanged (ADR-111).
- **G49.** *Added in revision 0.61.0 (decision 92).* **A team reaches the organisation's knowledge through one front door.** A **knowledge agent** is ordin in the agent profile, configured with the Git repositories it reads and the audience it serves; it reads each changed document in the background into the same memory graph every ordin uses (G48), and answers retrieval questions with ranked facts that name their repository, file and commit. A person adds a front door to a workspace themselves, with their company sign-in; when their own memory and folders are not enough, ordin sends the question — never the conversation — to the front door, which answers from its own graph and from other knowledge agents it asks in parallel, within deadlines, and returns one merged result labelled with what did not answer in time. No model call and no Git fetch happen while a person waits. Only knowledge agents answer; a person's own ordin never does. ordin's knowledge wiki is an **Open Knowledge Format** bundle: ordin writes and reads the Open Knowledge Format 0.2, so any tool that reads it reads ordin's pages, and ordin reads any team's bundle, glossaries included (ADR-112, ADR-113).
- **G9.** Nothing is dropped silently. When a session or crew starts, the application lists every part of a package and every declared rule that it does not carry across or does not enforce, by name.

## Non-goals

- **Building or editing agents.** AgentWright builds, reviews, fixes and improves packages. Hosting the builder's interviews inside the application is a later step, and a visual agent builder is postponed. *Withdrawn in revision 0.25.0: ordin makes agents through the agent maker (G40, ADR-083).*
- **Running wrightrun on the desktop as the local harness.** This was considered and rejected for now (ADR-002); it is reconsidered once wrightrun has code. *Moot from revision 0.43.0 (ADR-098): wrightrun is not built.*
- **A Claude Agent SDK runtime adapter in the first release.** *Withdrawn in revision 0.9.0:* Claude is now the first harness and Copilot the second, both in the first release (ADR-038).
- **Recurring duties and unattended work on the desktop.** A laptop sleeps, closes and goes offline. A package's recurring duty is reported as not carried across (G9); the duty belongs in wrightrun. *From revision 0.10.13 Ordin offers to ask IT to set repeating work up in wrightrun, and the application schedules nothing (ADR-060).* *From revision 0.18.0 the ordin server does not sleep, but schedules nothing either until OQ-38 is decided (ADR-073).* *Decided in revision 0.19.0 (decision 41): the server schedules nothing; its runs start from the person's chat and from NATS events (ADR-074).* *Amended in revision 0.43.0 (ADR-097): an ordin server in the agent profile runs recurring duties; the desktop and the personal profile still schedule nothing, and Ordin's request to IT asks for a hosted ordin agent.* *Amended in revision 0.53.0 (ADR-105): repeating work on a personal server is started by a standard scheduler outside ordin sending NATS events; ordin is the runtime and keeps no timetable.*
- **Serving agents to other people.** The application takes no inbound requests from Slack, webhooks or other users. It is a client of one person. *From revision 0.18.0 (ADR-073) the ordin server reads one paired person's chat by polling the chat service; it still takes no inbound connection and serves no one else.* *Amended in revision 0.42.0 (ADR-096): the server also takes connections to its Remote API from the person's own paired ordin desktops, on one private address chosen at setup, unless the profile forbids it; it still serves no one else.* *Amended in revision 0.43.0 (ADR-097): an ordin server in the agent profile serves the people the organisation allows, as one hosted agent acting under its own identity; the desktop and the personal profile still serve one person.* *Amended in revision 0.61.0 (ADR-113): a knowledge agent, in the agent profile, answers retrieval questions from its audience and from outside tools over a read-only MCP endpoint; a desktop and a personal server still answer no one.*
- **A web interface in a browser** (revision 0.42.0; ADR-096). The ordin server's Remote API serves ordin desktops only, through their own core; it serves no pages and is never offered on the internet.
- **Agents messaging each other directly.** Every message between crew members passes through the application (ADR-006).
- **Publishing packages to the marketplace.** Authors publish with APM and AgentWright's own tooling. *Withdrawn in revision 0.25.0: ordin publishes agents as pull requests to catalogue repositories (ADR-084).*
- **Local model inference for agents.** Local files and local tools do not mean a local model; Copilot's models run in GitHub's service. The one exception is memory's small embedding and reranking models (ADR-033).
- **Several people sharing one crew, memory, journal or workspace.** Each installation serves one signed-in person. People share work through Confluence and their own shared folders, not through ordin (ADR-025). *Amended in revision 0.38.0 (ADR-092): people also hand work to each other through ordin, as handovers carried by a Git repository or SharePoint folder they both use; nothing is shared between installations.* *Amended in revision 0.54.0 (ADR-106): or by a Jira issue they can both see.* *Amended in revision 0.43.0 (ADR-097): a hosted agent's memory and journal are the agent's, used by everyone who may talk to it and kept by scope; this is one organisation's agent, not people sharing an installation.* *Amended in revision 0.51.0 (ADR-103): people may also share knowledge through a team knowledge folder in a repository; each installation keeps its own memory and pages and takes the folder's files in as data, so nothing is shared between installations but those files.*
- **Two-way synchronisation with Confluence.** Local files are published out; an edit made in Confluence is shown and can be brought back as a copy, but it never changes a local file by itself (ADR-026). Ordin changing a document at its origin, after the person approves the push, is not synchronisation: it is one approved external action (ADR-029).
- **Screens written by a model.** Ordin chooses blocks and supplies their data; it never supplies markup, script or style (ADR-028).
- **People editing documents by hand inside ordin.** Ordin has agents make changes; the person can open any file in its own app (ADR-029). *Amended in revision 0.36.0 (ADR-048, ADR-057, ADR-070): by hand the person edits Markdown documents (with a formatting toolbar), knowledge pages, agents' own memory pages (with the same toolbar from 0.36.1) and email drafts (with the same toolbar). Everything else is changed by agents or opened in its own app (11 — UX guidelines §5.6).*
- **Wire compatibility with VS Code's Copilot extension.** Packages are loaded through the Copilot SDK and CLI, not through the editor.
- **Building editors of its own for documents, images or media.** Creating and editing those files is the ArtCraft apps' work. The code editor is the one exception (ADR-020); it edits text files only. *Amended in revision 0.36.0 (ADR-048, ADR-057, ADR-070): the code editor is no longer the only exception. ordin also edits Markdown documents and email drafts with a formatting toolbar, and knowledge pages and agents' own memory pages as text. Documents of other kinds, images and media are still edited only in the ArtCraft apps or in their own app.*
- **Parity with a full IDE.** The first release has no debugger, no notebooks, no remote development and no compatibility with VS Code extensions.
- **An interim route for office files.** Until WordCraft, GridCraft and DeckCraft read and write Word, Excel and PowerPoint files, agents do not edit those files, and no other library fills the gap (ADR-018). The application previews files, but edits them only through an ArtCraft app or the system's default app. *Amended in revision 0.36.0 (ADR-048, ADR-057, ADR-070): the hand editing named under* People editing documents by hand inside ordin *is the exception. Word, Excel and PowerPoint files open in the person's own Microsoft app, the system's default app; agents change Word through WordCraft and PowerPoint through DeckCraft, and do not change spreadsheets yet (11 — UX guidelines §5.6).*
- **Embedding ArtCraft apps' windows inside the application.** An app opens in its own window.
- **A memory shared between people.** Memory belongs to one person's installation (ADR-030). Until revision 0.8.0 this non-goal read "Elaborate memory automation … adds no memory store of its own"; ADR-030 replaced it with recall. *Amended in revision 0.43.0 (ADR-097): a hosted agent's memory is the agent's own, kept by channel, and a direct chat is never written to another scope.* *Amended in revision 0.51.0 (ADR-103): there is still no shared memory store; a Team Knowledge workspace copies its facts to and from a repository folder, and each person's memory stays their own.* *Amended in revision 0.60.0 (ADR-111): the links between things travel with the facts that state them; there is still no shared memory store.* *Amended in revision 0.61.0 (ADR-113): a knowledge agent's graph is built only from Git repositories its whole audience may read, never from a person's memory; a person's memory stays their own and is never reachable by others.*

## How a team works together through ordin

*Added in revision 0.51.0 (ADR-103).* Each person runs their own ordin; no installation is shared (ADR-025, ADR-092). People work together through places and channels they already use, in three ways:

- **Handing work over** (ADR-092). One person hands their results and a note to the next person through a Git repository or SharePoint folder they both use; a lifecycle says who comes next and what the work must hold. *Amended in revision 0.54.0 (ADR-106): or through a Jira issue, which ordin assigns to the next person.*
- **Telling each other in Slack** (ADR-102). A handover can be announced in Slack as the person, in a direct message or the stage's channel, with a link that opens it in the receiver's ordin; Ordin can read the Slack channels a workspace links and answer under the person's approval or a narrow rule.
- **Building up team knowledge** (ADR-103). A workspace in Team Knowledge mode shares all its memory facts and knowledge pages through a folder in a GitHub or GitLab repository: **Share what we've learned** sends them after one card, **Get them** takes in what colleagues shared. Each person's own database stays the working copy, and nobody needs to know Git. *From revision 0.59.0 (ADR-110), a workspace still shares to one folder, its own, and may also read any number of other teams' folders, read-only; nothing passes from one team's folder to another's unless a person adopts it, and a company may name folders that every applicable workspace reads.* *From revision 0.61.0 (ADR-112, ADR-113), the folder is also an Open Knowledge Format bundle with an index and a log, and knowledge agents can read it, read-only, so what a team shares can reach a wider audience through a front door.*

| Per-person source | A source only part of a knowledge agent's audience may open; every fact from it is checked for the asking person (ADR-115). *Added in revision 0.63.0 (decision 94).* | A repository with `audience-may-read: false` |
| Audience-open source | A source every member of a knowledge agent's audience may open, as the operator states; served without a per-person check (ADR-115). *Added in revision 0.63.0 (decision 94).* | A repository with `audience-may-read: true` |
| Sharing-change notice | A message GitHub or GitLab sends a knowledge agent when who may read a repository changes; it ends the remembered check answers for that repository at once (ADR-115). *Added in revision 0.63.0 (decision 94).* | A `member` event |
| Delegation | The Microsoft token a person's ordin sends with a question so a front door can check SharePoint files as that person, exchanged for one question and never stored (ADR-115). *Added in revision 0.63.0 (decision 94).* | — |
| Asker statement | The statement a front door adds to its own signed-in request to a proxy, naming the person it asks for and their linked accounts, so the proxy checks for that person (ADR-115). *Added in revision 0.63.0 (decision 94).* | — |
| Unchecked source | A source whose access check failed, was refused by the system or missed its deadline; its knowledge is withheld and the answer says only "Some sources couldn't be checked." (ADR-115). *Added in revision 0.63.0 (decision 94).* | "Some sources couldn't be checked." |
| Release | A version of ordin shipped to people, built with the build switches the release roadmap (kept by the maintainers outside the repository) sets for it; which features a release carries is planned there, not in this design (ADR-114). *Added in revision 0.62.0 (decision 93).* | a version that turns on `mail` and `slack` |
| Build switch | A Cargo feature of a program, named after the feature it turns on (`sandbox`, `copilot`, `mail`, `personal-profile`, `agent-profile` and others), that adds the modules of that feature to the build; a build without it composes none of them and answers none of their commands (ADR-114). *Added in revision 0.62.0 (decision 93).* | `telegram` |
| Module group | The commands of one module, named as the Service API names its group; a backend tells the screens which groups it answers, and the screens show nothing of a group it does not (ADR-114). *Added in revision 0.62.0 (decision 93).* | `mail` |
| Release feed | The one signed feed, in Tauri's updater format, that every release publishes with its desktop installers and server archives; desktop and personal server read it (ADR-114). *Added in revision 0.62.0 (decision 93).* | — |
| What's new | The card shown once after the first start of a new version, with that version's release notes; Settings › About shows it again (ADR-114). *Added in revision 0.62.0 (decision 93).* | "What's new in ordin 0.2.0" |
| Update key | The key that signs every release; its public half is built into every program, its private half held offline by the project's maintainers (ADR-114). *Added in revision 0.62.0 (decision 93).* | — |
