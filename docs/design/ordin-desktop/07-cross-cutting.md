## Cross-cutting Concerns

| Concern | Stance |
|---|---|
| Authentication | **Applies.** The application signs the person in to each external system with their own account: GitHub (Copilot), the organisation's OIDC provider (wrightrun), Slack (user token), Confluence (Atlassian OAuth), SharePoint (Microsoft account, revision 0.8.0) and email (the same Microsoft account with mail permissions, or a Google account; revision 0.15.0, ADR-070; and, first, the company's own mail server, by the company's single sign-on or the person's mail password kept in the keychain, over TLS only; revision 0.16.0, ADR-071). A refused mail password is never retried. Model vendors are the exception: each vendor harness signs the person in through its own flow and holds the credential; the application only checks the harness's sign-in state and starts its flow when needed (ADR-044). There is no application-level login. Opening the application on the person's computer is the local trust boundary. Tokens live in the OS keychain and are refreshed before expiry. An expired or revoked token pauses the run that needs it. *Agent profile (revision 0.43.0; ADR-097, ADR-098):* every request to a hosted agent but health, metrics and a signed intake carries an identity-provider token, verified for signature, issuer and audience in ordin's own code; an intake accepts its own token or a signature made with its shared secret; a chat event is accepted only over the link the agent's chat app opened. A desktop reaches a hosted agent with the person's company sign-in, never with a desktop key. *Knowledge agents (revision 0.61.0; ADR-113):* every knowledge query and MCP call carries an identity-provider token — a person's company sign-in from a desktop or an outside tool, a service identity from a front door or a tool — checked in ordin's own code; the groups claim the configuration names decides the audience. |
| Authorisation | **Applies.** Three layers, all decided in fixed code: (1) Tauri capabilities limit the WebView to the core's commands; (2) the Rules Engine decides every local tool request against the package declaration and the application policy; (3) the Crew Orchestrator decides every delegation against the charter's guardrails. Remote agents apply their own authorisation (wrightrun roles; Slack membership). *Agent profile (revision 0.43.0; ADR-097, ADR-098):* two roles from the token claim the configuration names: a caller starts runs and reads and resumes its own; an operator may do everything a caller may, plus the operator and work-folder routes. Approvers are named in the configuration; the asker never approves their own run's action that leaves the company. An intake may start its one command only. *Knowledge agents (revision 0.61.0; ADR-113):* by audience first. A knowledge agent reads only repositories its whole audience may read — the operator states this for each repository and the check refuses a repository without the statement — and answers only askers in one of its audience groups; a proxy answers a front door only when the configuration lists it and the access group it asks for is one of the proxy's own. Caches and the sources record are kept per access group and never shared across groups. Per-person checks against each asker's Git rights are a later decision. |
| Logging | **Applies.** Structured JSON lines with time, level, component, run identifier and crew-run identifier. Logs never hold tokens, message content, file content or tool arguments; arguments are logged as digests. Support export is a person's action and passes through a redaction step. *Fixed in revision 0.49.1 (`/spec`): every program writes one JSON object per line with wrightrun's keys first — `time`, `level`, `logger`, `event` — then the run, crew-run, thread and correlation identifiers, then the event's own fields. A field named `token`, `secret`, `password`, `authorization`, `signature`, `cookie`, `url`, `uri`, `dsn`, `address`, `content`, `body`, `arguments` or `prompt` is never written, and an error is logged by its code, never by its text.* *Knowledge agents (revision 0.61.0; ADR-113):* questions are never logged with their text, on the desktop or on any knowledge agent; logs, metrics and traces carry counts and timings only. The optional sources record holds answer ids and returned sources, never the question or the asker. |
| Metrics | **Does not apply** in the first release. There is no metrics endpoint. Run and crew counters are visible in the interface and the journal (A-10). *Agent profile (revision 0.43.0; ADR-097, ADR-098):* Prometheus counters on every instance, with wrightrun's counters carried across; names fixed in `/spec`. *Fixed in revision 0.49.1 (`/spec`), agent profile: the metric families are a closed list kept in the Telemetry component; a new family enters only by amending that list, and its name carries the `wrightrun_` prefix.* |
| Tracing | **Does not apply** in the first release. The journal links runs, rounds and tool requests by identifier. *Agent profile (revision 0.43.0; ADR-097, ADR-098):* OpenTelemetry spans per stretch of a run, sent to the organisation's collector only when switched on; no content, address or identifier of a person in a span; a span that cannot be sent is dropped and counted. *Fixed in revision 0.49.1 (`/spec`), agent profile: the Caller API does not read a caller's `traceparent`, so a run's trace starts at its own stretch span; every span on the allow list is recorded, and the only bound on volume is a queue of 2,048 spans waiting to be sent, whose overflow is dropped and counted.* |
| Rate limiting | **Applies, as budgets.** Request budgets per run and per crew (Copilot allowance), a limit on concurrent local sessions, one in-flight run per wrightrun thread (wrightrun ADR-064), and a minimum poll interval for the wrightrun and Slack adapters. Figures are in NFRs below and are fixed in `/spec`. From revision 0.10.14 the person's usage settings add model levels per kind of work, an estimate before heavy work, a limit on agents at once and an optional daily pause, within the profile's frame (ADR-062). *From revision 0.19.0, on the ordin server, triggers: one run at a time per trigger, up to 10 waiting, and at most 20 triggered runs a day per installation (ADR-074).* *Agent profile (revision 0.43.0; ADR-097, ADR-098):* the limits a package or configuration declares (starts of a command, of a scope or of an asker per period; runs in progress per intake; suppression of a repeated message), counted exactly in the datastore; a thread takes one run at a time. *Fixed in revision 0.49.1 (`/spec`): on the personal server, each paired desktop may send 50 Remote API commands a second, in bursts of up to 100; on the agent profile, the Caller API holds at most 100 open requests and refuses more. No caller, role, origin or program is exempt from any limit.* |
| Pagination | **Applies** to adapter reads that page: Slack thread replies, wrightrun listings and APM listings. The interface paginates the journal and artefact lists. *From revision 0.25.0 there are no APM listings: the agent library pages through the Catalogue Service's local index, and the GitHub reads behind pull requests and reviews page through `gh` (ADR-082, ADR-084).* |
| Input validation | **Applies.** At the Command Bridge (every command from the WebView), at charter load (schema and references to installed instances and registered remote agents), at workflow save and import (from revision 0.11.0, ADR-064: file size at most 256 KB, format and format version, agents matched in the workspace, inputs and earlier results each step uses, limits lowered to the company's maxima — in fixed code, never by a model; *from revision 0.12.0 (ADR-065, ADR-066)* also every control block's paths, condition and maximum, nesting depth, results used only where they exist, and calls between workflows without a cycle, on every version read from a repository as on every import), at declaration load (the format wrightrun's spec fixes), and on every adapter response before use. *From revision 0.25.0 (ADR-082, ADR-087) also every part read from an agent repository, in either format, by the Checker before it is offered, and every draft before it is tried or published.* Package, remote and fetched text is data and never instructions. |
| Fixed-code decisions (revision 0.25.0; ADR-085) | **Applies** to everything the agent machinery does. An agent may suggest content only: the words of a purpose, a job, a rule or a skill. Matching a request against the library, generating every file from a draft's fields, the wording rules, every check, each rehearsal expectation, the bundle, lock file and digests, the pull request's contents, reading, pinning and withdrawal, and every format plug-in's *read* and *write* (ADR-087) are ordin's Rust code, whose result for a given input is the same every time, with no model call in the decision. Model-scored checks are shown as opinions, labelled as coming from a model, and never gate. An authoring tool call that carries file contents is refused. Each gate has table-driven tests over frozen crucible's fixtures. This extends the fixed-code checks of blocks (ADR-028) and workflow files (ADR-065). *Amended in revision 0.55.0 (ADR-107): applies also to hosted agents' runs. Whatever must happen on every run — screening a question or an answer, gathering context before the model — is done by ordin in fixed code, in a fixed order, switched on and sized in the agent configuration, and never left to the model's choice or the package's instructions.* |
| Error handling / envelope | **Applies.** Typed errors in the core, with a stable code. The person sees only a plain-language sentence with at most one action ("Try again", "Sign in again", "Send to IT"); codes, tool output and stack details appear only in Diagnostics and in help requests. The application tries an automatic repair before it shows an error (Setup Assistant). No internal state leaks into a message. Codes are fixed in `/spec`. *Amended in revision 0.49.0 (decision 80): when two parts of ordin would raise codes with the same prefix, wrightrun's carried codes keep their names, because hosted-agent clients already read them, and ordin's new codes are renamed: workflow-file codes take `WFF_`, tool-request codes `TREQ_`, and a release reference conflict uses wrightrun's `REL_EXISTS_DIFFERENT`; `SRV_` is shared by wrightrun's carried codes, the Remote API's routing refusals and the paging-cursor code; every other prefix has one owner. *Amended in revision 0.49.1 (`/spec`): the prefix list and the full code registry are kept in the low-level design's Error Handling specification, regenerated from the component specifications; a code missing from it fails the build.* The prefix list itself is kept in the low-level design (1A SA-ERR-01).* |
| Configuration | **Applies.** Technical settings come only from the signed organisation profile: marketplace (*from revision 0.25.0 the agent repositories, ADR-082*), trust policy (*over tool bindings and hooks*), remote agent catalogue, Slack channel, identity settings, limits and update feed (ADR-013). The person's own settings are limited to non-technical choices: retention within the profile's bounds, notification preferences and display. *From revision 0.27.0 (ADR-086) the profile also says whether the person may add agent repositories (default: yes). Repositories the profile names are shown as* Set by your company *and cannot be removed by the person; the person's own additions, each with the display name they gave it, are kept in Settings › Agent repositories. When the profile turns adding off, the library and Settings say that the company manages the agent repositories, with* Send to IT. No setting holds a secret; secrets live in the keychain. *Amended in revision 0.49.1 (`/spec`): the one exception is the organisation profile's `google.client_secret`, the non-confidential secret of the Google Workspace desktop sign-in client, sent in the token exchange.* Per-package configuration comes from the package, and per-crew configuration from the charter. *Amended in revision 0.48.0: settings do not come only from the organisation profile. They reach ordin from four sources: fixed constants in code (including each application maximum); settings the installer carries (the two addresses needed before the profile can be read); the organisation profile's company defaults and maxima; and the person's own choices in Settings, or, on the ordin server, the server owner's choices at setup. The agent profile reads no organisation profile: its per-agent choices come from the agent configuration file in the agent release (ADR-098). No setting lives in two sources.* *Knowledge agents (revision 0.61.0; ADR-113):* a knowledge agent is configured by the `knowledge` section of its agent configuration; a desktop's front doors are the person's own choice, with optional defaults named by the organisation profile that the person can remove. *Amended in revision 0.62.0 (ADR-114): each program is built for one release; Cargo features of the program, one per release, decide which modules it composes, and a backend tells the screens the module groups it answers.* |
| Health checks | **Applies, locally.** The Setup Assistant runs the checks at start, in the background and on demand, and repairs what it can before telling the person. It checks: each vendor harness the profile names is installed at a tested version and signed in; the ordin hook answers; the GitHub sign-in is valid; each registered remote agent is reachable; the Slack token is valid; *from revision 0.25.0 each agent repository's clone can be fetched with the person's sign-in (ADR-082, ADR-086). Until revision 0.25.0 it also checked that the bundled `apm` responds.* There is no health endpoint. *On the ordin server (ADR-076): systemd's watchdog every 30 seconds or the container's health check; the harness sign-in every 6 hours; each channel and NATS reconnected without end, with an outage over 10 minutes reported on the other channel.* *Agent profile (revision 0.43.0; ADR-097, ADR-098):* every instance serves liveness and readiness without a token; an instance whose release fails to load never reports ready; a chat-role instance is ready when the datastore and its chat link are open. *Fixed in revision 0.49.1 (`/spec`), agent profile: an instance is ready when the datastore answers a ping within 2 seconds, the Memory Service answers where the role started it, and, in the chat role, every chat link is open; a check not answered within 2 seconds counts as not ready, and readiness drops at once when the instance starts to stop.* |
| Migrations | **Applies.** The SQLite journal schema is versioned and migrated forward on start, in one transaction, after a backup copy. A database newer than the application is refused with a message, not downgraded. *Agent profile (revision 0.43.0; ADR-097, ADR-098):* the schema is versioned with ordin and applied by the schema command (a Helm hook in the scaled shape) before a release's instances start; within one minor line a change only adds; an instance stops on a schema older than it needs. *Fixed in revision 0.49.1 (`/spec`): on every program, a migration step that drops or narrows anything, or adds a required column without a default to a table that holds rows, is allowed only at a minor or major version change of ordin, and its specification states how to roll it back; within one minor line a step only adds.* *Amended in revision 0.54.0 (ADR-106): a step that only adds values to a closed list of allowed values may rebuild the table to do so — SQLite cannot change such a list in place — when every row and every row that refers to it is kept and a migration test proves it; such a rebuild counts as adding, not dropping.* |
| Graceful shutdown | **Applies.** On quit, the application asks before ending running sessions. It flushes the journal and stops CLI servers, giving each a stop deadline. Remote runs continue remotely and are reconciled on next start. On system sleep, local sessions pause where the SDK allows; otherwise they are marked *interrupted* on wake. *On the ordin server, `SIGTERM` flushes the journal and gives each session its stop deadline; runs are recovered on next start (ADR-073).* *Agent profile (revision 0.43.0; ADR-097, ADR-098):* an instance told to stop takes no new run and lets its runs finish within the stop period; a run still executing when its instance ends is recorded as interrupted and not started again; a worker records each job's checkpoint before it exits. *Fixed in revision 0.49.1 (`/spec`, decision P4-2): the ordin server's personal profile stops the same modules as the desktop, in the desktop's order, after its own inputs; each step has 2 seconds, except the chat outbox drain (10 seconds) and the Remote API's requests in flight (5 seconds); runs may finish until 30 seconds after the signal and are then cancelled and recorded as interrupted; the stop ends within 54 seconds, inside the service manager's 60-second stop timeout (systemd `TimeoutStopSec=60s`, container stop timeout 60 seconds). The agent profile never cuts a run short: a run still executing when its instance ends is recorded as interrupted by another instance when its lease lapses.* |
| CORS | **Does not apply.** There is no HTTP server. The WebView loads only bundled assets. *From revision 0.18.0 the ordin server has no HTTP server either; it polls the chat service (ADR-073).* *Amended in revision 0.48.0 (ADR-096, ADR-098): "there is no HTTP server" no longer holds for the ordin server, and CORS still does not apply, for each program in turn. Desktop: no HTTP server; the WebView loads bundled assets only. Personal server: it listens only for the Remote API, on one private address chosen at setup; the Remote API serves no browser pages and sends no CORS headers, and a request carrying an `Origin` header is refused, since only ordin desktops call it. Agent profile: it serves the Caller API, which servers call, and sends no CORS headers.* |
| Internationalisation | **Applies, from the first release** (ADR-042). Every interface string is a Fluent catalogue message shared by the core and the WebView; the locale follows the operating system, changeable among the locales the profile offers; CLDR formatting of dates, numbers, plurals, lists, sorting and time zones; right-to-left layout; Ordin converses in the person's locale; approval-card text is never model-translated; a missing catalogue entry fails the build. *Amended in revision 0.58.0 (ADR-109): the person's edits and own languages are served from ordin's own storage beside the compiled-in catalogues, never from the network or the profile; every message entering them passes one fixed check against en-GB; a drafted or imported language's safety wording is used only after the person checks it; no model is called to show a message; message text is never logged. Ordin is told the person's language in its seed.* |
| Branding (white label) | **Applies** (ADR-041). A brand pack sets the product name, coordinator name, logos, icon set, design tokens, fonts, links and legal text: the build layer through a branded build, the run layer through the signed organisation profile. Approval-card structure, danger and waiting colours and the accessibility baseline are fixed; a brand failing WCAG 2.2 AA contrast is refused. |
| Multi-tenancy | **Does not apply.** One installation serves one person. Agent folders isolate agent instances from each other, and workspaces separate pieces of work; neither separates tenants. *Agent profile (revision 0.43.0; ADR-097, ADR-098):* still does not apply: one installation is one agent of one organisation. Content is kept by scope (channel, direct chat, agent-wide), which separates channels inside one organisation and is not a tenant boundary. *Knowledge agents (revision 0.61.0; ADR-113):* a knowledge agent serves its audience as one organisation, not as tenants; access groups separate caches and sources records, not data. |
| Latency of knowledge answers (revision 0.61.0; ADR-113) | **Applies.** No model call and no Git fetch on a question's path at a front door or a proxy: they search graphs already built, and the reply is written by the person's own ordin. Every query carries a deadline: the front door returns what has arrived by 1 s and sends later results as **More found** until 5 s, naming what did not answer in time; a backup proxy covering the same repositories is asked after 300 ms; a hop budget (1 by default) and a list of agents visited stop loops; answers are cached by question, access group and the commits they relied on, and dropped within 10 s of a repository moving; front doors keep connections to proxies open and may read a repository themselves when they ask about it often (A-62 to A-64; C-95, C-96). |
| Open Knowledge Format (revision 0.61.0; ADR-112) | **Applies.** ordin writes and reads the Open Knowledge Format 0.2 wherever it writes or reads knowledge: a workspace's knowledge folder, a team folder and every repository a knowledge agent reads. ordin's own keys are extensions and never replace a format key; keys and `sources` fields ordin does not own are kept byte for byte when a file is rewritten; unknown types, unknown keys, broken links and a missing `index.md` are never errors; `index.md` and `log.md` are never pages. Trust is derived from verification (human-reviewed, machine-confirmed, unverified) and ranks recall. A future major version is read only after a decision to adopt it. Until the format's licence is confirmed (C-97), documentation says ordin "writes and reads the Open Knowledge Format 0.2". |
| Releases and updates (revision 0.62.0; ADR-114) | **Applies.** ordin ships in increments planned in the release roadmap (kept by the maintainers outside the repository); each build composes only the modules its build switches turn on. Every shipped version is signed with the one update key and published in one release feed; nothing unsigned or older than the running version is installed. The desktop updates in the person's own account with no administrator (ADR-072); a personal server replaces itself only when the person asks; the agent profile is updated by its operator. The Journal copies the datastore before a new version's first migration, and a release is undone by restoring that copy with the previous version. |

## Non-functional Requirements

- **Performance targets.**
  - Interface actions that do not wait for a model respond within 150 ms at the 95th percentile (A-03).
  - Application start to an interactive Start view takes under 3 s on a supported machine, excluding sign-in (A-03).
  - A local session's first progress event reaches the interface within 1 s of the SDK emitting it.
  - *From revision 0.42.0 (ADR-096, A-46):* on the company network, a Remote API command that does not wait for a model answers within 150 ms at the 95th percentile, and an event reaches the desktop's screens within 500 ms of the server's journal recording it.
- **Scale.**
  - Up to 8 concurrent local sessions (A-04).
  - Up to 50 installed agent instances.
  - Crews of up to 8 members plus the coordinator.
  - A journal of up to 100,000 runs before pruning.
  - *Agent profile (revision 0.43.0; A-48, A-49):* the scaled shape carries wrightrun's targets for one hosted agent — up to 100 runs at once, up to 20,000 runs a day, work-folder files of up to 10 MB — with each run instance running at most 10 harness processes at once by default; the single shape, up to 8 runs at once.
- **Crew guardrail defaults**, which a charter may lower but never raise above the application maximum (A-05):
  - 10 rounds (maximum 30);
  - a 60-minute wall-clock limit (maximum 8 hours);
  - escalation after the same member fails twice in a row;
  - 4 members running at once (maximum 8);
  - a request budget set by the charter, with no default ceiling until OQ-3 is answered.
- **Availability.**
  - A desktop application has no service-level objective. A crash loses no completed step: every completed step and every external action is journalled before the next begins.
  - Offline: browsing installed agents, results and memory works offline. Starting a run needs the network.
- **Security posture.**
  - Least privilege: an agent-folder-only file scope by default. Other places only by the person's grant in the workspace a run started in, given for folders added through the system folder picker or by drag and drop (ADR-025). Protected system locations can never be granted.
  - In projects, an agent writes files only through the change set, and runs check commands and GitHub operations only through the Rules Engine. GitHub write operations need the engineer's approval unless the engineer has switched it off for that kind in the project, within the organisation profile's ceiling.
  - The terminal is the engineer's alone: no agent can read from it or write to it, and its content is not journalled or logged.
  - Craft CLIs run with paths limited to granted places, a time limit per call, and no network access requested by the application.
  - Shell commands are allowed only for an instance whose package authority is system-changing; each command needs approval unless the package declares a rule that allows it (A-06).
  - No arbitrary shell from the interface.
  - Approvals for externally visible actions.
  - Credentials only in the keychain.
  - Redacted logs.
  - Policy enforced outside prompts.
  - User space only (ADR-072): no administrator rights at any step; no system service, driver or system extension; programs, data and secrets only in the person's own account; local channels on loopback or in the application data root; company allow-listing respected, never worked round.
  - The ordin server (ADR-073): one person per installation, an ordinary user account, no inbound port (the chat is read by long polling) *(amended in revision 0.48.0, ADR-096 and ADR-098: the personal server listens only for the Remote API, on one private address chosen at setup, and opens no other port; the agent profile serves the Caller API)*; only the paired chat account is answered; a typed message is never an approval and no secret is accepted from the chat; approval buttons carry single-use references checked by the Approval Service; the profile lists the allowed chat channels (A-40) and can switch off chosen kinds of external action on the server.
  - Triggers (ADR-074): only subjects in the profile's list; filters in fixed code with no model turn; event content reaches agents only as named, size-limited inputs; at most 20 triggered runs a day per installation by default; every external action of a triggered run still needs the person's approval.
  - Telegram tools (ADR-075): only chats a workspace links; the paired private chat never exposed; no tool posts; every post from an approval card in the paired chat; linked chats' messages never act as commands.
  - Slack tools and notices (ADR-102): only channels a workspace links, read with the person's own token; direct messages never read; no tool posts; every post as the person, from an approval card that named it or under a rule the person set once (one kind, one channel, a daily cap), which the profile can turn off; linked channels' messages never act as commands; Ordin looks at them only when the person turned that on, within fixed daily limits.
  - Slack channel (ADR-076): Socket Mode, so no inbound port; only the paired Slack user's direct message with the app is answered; its bot and app-level tokens kept apart from the person's own Slack user token (ADR-008).
  - Team knowledge (ADR-103): only the folder a workspace binds, read and written with the person's own sign-in; no service but the repository host is contacted; every share from one approval card, pushed without force and never rewriting history; files from the folder are data, checked for size and fields, and every fact passes the write gate's personal-data and instruction checks; never shared: facts used in all workspaces, facts from page sections, facts awaiting the person's check for personal data, search vectors and usage fields. *Amended in revision 0.59.0 (ADR-110):* nothing got from another team's folder is ever shared on, except an item a person adopts, which passes the personal-data scan, the instruction check and the write gate again; adopting is a person's action only; folder descriptions and recall checks are data; folders the company names are read with the person's own sign-in, the profile grants no access, and one that must be reviewed is read only while ordin can see the review rule.
  - Agentic memory (ADR-111): every agent session's memory writes go through the Memory Service under the agent's memory rules, links and summaries included; statements, thing names, other names and link words are never logged, journalled or sent in telemetry — journal entries for memory actions carry ids and counts only; names and link words pass the same personal-data scan and instruction check as statements, and a name with a likely personal-data finding is dropped rather than kept redacted; the recall record holds ids only; a link is followed in recall only when the reader may read a current fact that states it; every change to memory the person sees is the person's own action, and nothing new leaves the computer.
  - Knowledge agents (ADR-113): only knowledge agents answer, in the agent profile; a desktop or personal server only asks, so a person's memory is never reachable by others; a desktop sends only the question and its filters, never the conversation, workspace facts or file contents; knowledge agents read Git read-only and write no page and nothing to any repository; the MCP endpoint is read-only — no tool writes, forwards a conversation or runs anything; statements, names, link words and tables of contents from documents and from other knowledge agents are data, never instructions; a request whose visited list holds the agent is refused. *Amended in revision 0.63.0 (ADR-115): no component stores who may read a document; a person's sign-ins reach a knowledge agent only to link accounts, and are dropped; a delegated Microsoft token lives for one question; check answers stay in the agent's process.*
  - The Remote API (ADR-096): served to the person's own paired desktops only; one private address chosen at setup, which the profile can forbid, with the server owner's certificate and, if the profile says so, client certificates; never the internet and no browser pages; every call carries a desktop key over TLS 1.3, kept on the desktop in the keychain and on the server as a hash; 10 failed key checks a minute from one address close it for 10 minutes; a press from a desktop is checked by the Approval Service as a chat button press is; the desktop's WebView makes no network call.
  - A hosted agent (revision 0.43.0; ADR-097, ADR-098): who may reach it is closed by default and printed in the start-up report; it holds the organisation's model key, which reaches Claude Code only, and each connection's own credentials, never a person's; connections expose only the operations the configuration lists; bundle paths are read-only and the work folder is reached only through ordin's file tools; no shell unless granted, and then only in the sandbox; a package's gates and argument rules cannot be weakened by the configuration; an agent release is loaded only when its digest matches, and who may publish one is set in the registry's access control; code reaches an instance only through the image.
  - **Threat model summary:**
    - a hostile package (mitigated by audit, approval of executable parts, and the rules engine; *from revision 0.25.0 the Checker on every part read, the trust policy over tool bindings and hooks, and the review on GitHub before an agent is published, ADR-082, ADR-084*);
    - prompt injection through documents or remote replies (mitigated by fixed-code policy and approvals for externally visible actions);
    - stolen tokens (mitigated by the keychain and expiry);
    - a runaway crew (mitigated by guardrails and the kill switch);
    - a document steering Ordin (mitigated by Ordin having no action tools of its own, approval cards built only by the application, an approved push for every change to an origin, and the memory component's write gate; R-27);
    - agent-written code in Python, shell or JavaScript (mitigated by the sandbox: no network except through the broker, no files except those passed in, no tokens; ADR-031, ADR-040);
    - a harness tool call that bypasses approval (mitigated by the ordin hook failing closed, the MCP Front deciding every service call itself, and the harness's shell and code tools switched off; ADR-037, ADR-045);
    - a rebrand that hides safety cues (mitigated by fixed approval cards and run-state colours, and the contrast check; ADR-041);
    - eavesdropping through dictation (mitigated by capture only while the person dictates, on-device recognition and no stored audio; ADR-043).
    - a stolen chat account or bot token on an ordin server (mitigated by pairing to one user identifier in a private chat, pairing changed only over SSH, **/stop**, the bot token in the server's secret store, and the profile's switches; R-62, ADR-073);
    - company content read by the chat service (mitigated by the profile allowing each channel, and full card content sent only on **Show details**; R-63).
    - text in a NATS event steering an agent (mitigated by fixed-code filters, inputs of at most 4,000 characters, event content treated as data, and approvals; R-65);
    - a flood of events spending the person's plan (mitigated by one run at a time per trigger, a queue of 10 and the daily limit; R-64).
