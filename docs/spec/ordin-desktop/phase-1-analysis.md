## 1A — Assumptions Register

The HLD's own assumptions are **binding inputs** and are not restated here: A-01 to A-49 (A-14 and
A-26 are withdrawn in the HLD and bind nothing). Its decisions (ADR-001 to ADR-099), confirmation
results and settled Open Questions bind in the same way. The rows below are **LLD-level assumptions**:
concrete defaults this spec set picks, under rule S6, wherever the HLD defers a choice to `/spec` or is
silent and a sane default exists. Each row is the value every Phase 2–5 artefact assumes until the row
is amended.

Library picks were checked on January 2026 against the crates.io and npm registries (latest stable
version, its declared licence, and the date of its last release) and, where noted, against the
project's own status page. Every licence named is OSI-approved and is neither the GPL nor the AGPL
(05 — Tech stack, *Licence and vulnerability checks*). A version named here is the version the
workspace pins at first lock; Phase 5 may raise it within the same major line.

Names marked *chosen here* are spec decisions made in this phase, not identifiers found in the HLD
or the repository.

| SA-ENV-01 | Error envelope — Service API and Remote API | A Service API command replies with the 2C wire `CommandReply`: `{"request_id": "<id>", "kind": "ok", "result": <result>}` or `{"request_id": "<id>", "kind": "error", "error": {"code": "<ERROR_CODE>", "message": "<one plain-language sentence>", "action": "try_again" \| "sign_in_again" \| "send_to_it"}}`, `action` omitted when there is none. | SA-ERR-01 | Error-code naming | Error codes are `SCREAMING_SNAKE_CASE` with an area prefix and one underscore after it (`<PREFIX>_<NAME>`, for example `RULES_DENIED`), held in **one error registry** in Phase 4 *Error Handling*: code → class, HTTP status (or none), exit status, plain-language sentence id, action. | SA-I18N-00 | Locale default | The default and fallback locale is `en-GB`. Code comments and spec prose are en-GB (output-language layer rule). | ADR-042; OQ-30 leaves further first-release locales open and does not block `/spec`. | Adding locales adds catalogues only. | 07 — Internationalisation; OQ-30 |
| SA-CFG-01 | Configuration precedence — desktop and personal server | Values resolve in this order, later wins: (1) compiled defaults; (2) the signed organisation profile, which sets values **and** ceilings; (3) the person's own settings, for keys the profile marks as the person's (non-technical choices of 07 — *Configuration*), each clamped to the profile's bounds. On the ordin server, the setup command writes the server's own settings file (profile address, listening address and port, channel pairings) under the application data root; it sits at level (2½): below the profile's ceilings, above the person's settings. No level holds a secret (secrets live in the keychain or the server's secret store). | 07 — *Configuration* and ADR-013: technical settings only from the profile; person's settings are non-technical and within bounds. | A different order would let a person exceed a company ceiling; Phase 6 audits every setting key against this order. | 07 — Configuration; ADR-013, ADR-086 |

### Configuration pass (2D)

1. **Where the update feed comes from.** `02-architecture.md:699`, `04-domain.md:27`, `07-cross-cutting.md:22` and ADR-013 (`09-decisions.md:221`) put the update feed in the organisation profile, and ADR-013 rejects "settings baked into the installer"; ADR-041 (`09-decisions.md:761`) puts the update feed in the branded build, set by the installer. 2. **History retention bounds.** `07-cross-cutting.md:22` says the person sets "retention within the profile's bounds"; A-08 (`10-risks.md:19`) and `04-domain.md:386` let the person enter any whole number of days of at least 1, with no profile bound, and no profile list (`02-architecture.md:691`–`700`, `08-interfaces.md:77`) names a retention bound.
