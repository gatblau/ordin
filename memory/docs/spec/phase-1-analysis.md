This phase turns the agentic-memory HLD (revision 0.4.0) into the analysis substrate the
component and cross-cutting specs are built on. Per rule S6 (*assumptions over questions when

## 1A — Assumptions Register

The HLD's own assumptions (ASSUMP-*) and decisions (ADR-*) are binding inputs; they are restated in
the Glossary and the architecture phase. The rows below are **LLD-level assumptions** — concrete
defaults the spec picks to make components implementable in a single prompt. Each is the value the
spec assumes unless the corresponding HLD Open Question is later resolved differently.

| ID | Area | Assumption | Rationale | Impact if wrong |
|---|---|---|---|---|
| SA-ID-01 | Identity format | Every stored record (Fact, Entity, Relationship, Source) is keyed by a server-generated **UUIDv7** rendered as a 36-char lowercase string; the SurrealDB record id is `<table>:⟨uuid⟩`. | UUIDv7 is time-ordered (good index locality for bi-temporal scans) and globally unique without coordination across tenant namespaces. | Switching to ULID/UUIDv4 is a string-format change confined to the Memory Store id helper; no contract field changes type. |
| SA-ENV-01 | Error envelope | Every error response is the single shape `{"error": {"code": "<MACHINE_CODE>", "message": "<human text>", "correlation_id": "<uuid>"}}`; every success response is `{"data": <payload>, "meta": {...}}`. | HLD 07 mandates *one* success and *one* error envelope with machine `code` + human `message`; correlation id makes every response traceable. | A shape change touches the shared envelope type and every handler; caught early by the Phase 6 "documented on both sides" audit. |
| SA-ENV-02 | Error code registry | Error `code` values are SCREAMING_SNAKE_CASE drawn from one central registry (Phase 4 Error Handling spec); no handler invents an ad-hoc code. | A closed registry lets agents branch on `code` without parsing prose. | An unregistered code leaks; the Phase 4 spec is the single source and the audit checks every error-table row against it. |
| SA-SCORE-01 | Score types | `confidence` and `salience` are `f64` constrained to the closed interval `[0.0, 1.0]`; persisted as SurrealDB `float`; validated at write. | The concept notes treat both as probabilities/importance in [0,1]; one type avoids per-call-site clamping bugs. | A range change is a validation-rule edit in the Write Pipeline and Memory Store; stored values stay valid under a widened range. |
| SA-TIME-01 | Temporal model | All timestamps are UTC RFC 3339 with millisecond precision. A Fact carries `valid_from` (required), `valid_to` (nullable — open interval = currently true), and `ingested_at` (required, set server-side). | Bi-temporal model (ADR-002) needs two timelines; nullable `valid_to` encodes "still true". | A precision/zone change is confined to the time helper; stored values remain parseable. |
| SA-VIS-01 | Visibility enum | Fact `visibility` is one of exactly `user-private` (default), `team-shared`, `tenant-shared`. No other value is accepted. | HLD 04/07 name exactly these three levels under ADR-011. | Adding a level is an enum extension plus an authorisation-rule row; existing data defaults to `user-private`. |
| SA-CLASS-01 | Memory class enum | Fact `memory_class` is one of exactly `episodic`, `semantic`, `consolidated`. `procedural` is rejected with `VAL_UNSUPPORTED_CLASS` (HLD non-goal). | HLD 00 defers procedural memory explicitly; rejecting it keeps the door closed without silent acceptance. | Re-enabling procedural is an enum extension; no stored value becomes invalid. |
| SA-PAGE-01 | Pagination | Recall and any list response use **opaque cursor** pagination (`meta.next_cursor`, nullable); the cursor encodes (score, record-id) for a stable total order. Default page size 20, max 100. | HLD 07 mandates bounded, capped, paginated, token-efficient results; cursors are stable under concurrent writes where offsets are not. | Cursor encoding is internal to the Retrieval Engine; changing it does not change the response contract (cursor is opaque to callers). |
| SA-CAP-01 | Result cap | `POST /v1/recall` accepts `result_cap` in `[1, 50]`, default 10; the response never exceeds it. | Keeps a recall response inside the single-digit-thousands token budget (NFR-P5). | The cap is a config-backed constant; raising it risks NFR-P5 and is a config change, not a contract change. |
| SA-IDEM-01 | Idempotency | Every write (`remember`, `retire`, `delete`) requires an `Idempotency-Key` header (1–255 chars). The (scope, key) pair is stored with the original outcome for **24 h**; a replay inside the window returns the original result with no new side effect. | HLD 03/08 mandate idempotent acks; a bounded retention window stops unbounded key growth. | Window length is a config value; too short risks duplicate writes on slow retries, caught by the Remember Gherkin replay scenario. |
| SA-JWKS-01 | OIDC discovery cache | `memory` fetches `.well-known/openid-configuration` and the JWKS at startup and refreshes the JWKS every **3600 s**, plus an on-demand refresh (rate-limited to once per 60 s) when a token presents an unknown `kid`. | Standard JWKS rotation handling; avoids a network fetch per request while tolerating key rotation. | Cache TTL is config; too long risks rejecting freshly-rotated keys until the on-demand refresh, which mitigates it. |
| SA-QUEUE-01 | Work queue | The durable work queue is **store-backed** (a SurrealDB `work_job` table with a claim/lease protocol) by default, preserving the single-binary story; the queue is accessed through a `WorkQueue` trait so a NATS backend can replace it without touching producers/consumers (OQ-QUEUE). | ASSUMP-QUEUE + HLD 05 prefer a store-backed queue to keep one binary; the trait keeps the product swappable. | A backend swap is a trait-impl change; job payloads and the producer/consumer contract are unchanged. |
| SA-QUEUE-02 | Job retry | A failed job is retried with exponential backoff (base 2 s, factor 2, jitter ±20 %, max 5 attempts), then moved to a `dead_letter` table for manual reprocessing. | HLD 03 Remember error posture mandates bounded retry-with-backoff then dead-letter. | Backoff numbers are config; tuning them does not change the job contract. |
| SA-DECAY-01 | Decay model | Salience-adjusted retrievability follows an Ebbinghaus form `R = exp(-Δt / (s · k))` where `s` is per-fact stability (raised on each recall/reinforcement) and `k` a global constant; a Fact is a prune candidate when `R < 0.05` **and** `salience < salience_floor` (default floor 0.3). | ADR-006 commits graceful, reinforcement-resettable decay with a salience floor; the exponential form is the standard Ebbinghaus model from the concept notes. | The curve and floor are config; the model is isolated in the Maintenance Worker decay function and unit-tested against a table of cases. |
| SA-RECENCY-01 | Recency weighting | Final read-path ranking is `final = rerank_score · (1 + recency_boost)` where `recency_boost = w · exp(-age_days / τ)` (default `w=0.15`, `τ=30`). | ADR-005 names recency weighting after rerank; an explicit small bounded boost keeps it from dominating relevance. | Weights are config; isolated in the Retrieval Engine ranking function, unit-tested. |
| SA-GATE-01 | Retrieval gating (abstain) | A recall abstains (returns zero facts with `meta.abstained=true`) when the top reranked candidate's score `< abstain_threshold` (default 0.2). | HLD 03 mandates "abstain rather than pad"; an explicit threshold makes the behaviour testable. | Threshold is config; too high over-abstains, caught by the abstain Gherkin scenario. |
| SA-WGATE-01 | Write gate | The write gate scores trust in `[0,1]`; `≥ trust_admit` (default 0.7) → persist; `trust_quarantine ≤ score < trust_admit` (default 0.4) → quarantine table; `< trust_quarantine` → reject. Instruction-like content (imperative-pattern detector) is capped below `trust_quarantine`. | ADR-008 commits quarantine-not-hard-reject for the uncertain; thresholds make the three-way outcome concrete. | Thresholds are config tuned against labelled data; isolated in the Write Pipeline gate function. |
| SA-PII-01 | PII handling | On the write path a PII detector runs; a span flagged with confidence `≥ pii_redact` (default 0.9) is redacted in place (replaced by `‹redacted:‹type››`); a lower-confidence flag stores the fact with `pii_review=true` for later review. | HLD 06 commits "redact when flagged with high confidence, flag-for-review otherwise". | Thresholds are config; the detector is an injected trait so its implementation is swappable. |
| SA-EMBED-01 | Embedding contract | The embedding provider returns a fixed-dimension `f32` vector; dimension is read from config (`MEMORY_EMBED_DIM`, default 1024) and must match the SurrealDB vector index dimension at startup (readiness fails on mismatch). | OQ-MODELS leaves the provider open; pinning dimension to config with a startup check prevents silent index corruption. | A dimension change requires a re-embed migration (Maintenance Worker) and an index rebuild; the startup check makes the mismatch loud. |
| SA-RERANK-01 | Rerank candidate set | Stage-1 recall returns up to `stage1_k` candidates (default 50) to the cross-encoder; the reranker scores all of them; the top `result_cap` survive gating. | ADR-005/012 bound the rerank set; 50 keeps rerank inside its NFR-P2 sub-budget. | `stage1_k` is config; larger sets cost read-path latency, smaller sets cost recall. |
| SA-LAT-01 | Read-path latency sub-budgets | Within NFR-P2 (p95 ≤ 200 ms): query-embed ≤ 60 ms, stage-1 ANN ≤ 50 ms, cross-encoder rerank ≤ 60 ms, in-process overhead ≤ 5 ms. On sub-budget breach the step degrades (skip rerank → stage-1 order) rather than blocking. The read path performs no freshness check (ADR-014). | ADR-012 requires explicit per-inference sub-budgets summing within NFR-P2; degradation keeps the path inside budget. | Sub-budgets are config; they are asserted in integration tests against the target corpus (OQ-VOLUMES pins absolute numbers). |
| SA-FRESH-01 | Freshness placement | Freshness is **agent-side** (ADR-014). `memory` performs no source-change check, makes no outbound broker call, enqueues no re-read job, and returns no `currency`; the agent (with its co-located broker) runs ask→check→update and uses the existing write/supersede endpoints for the refresh. | The broker is a per-agent local component a central `memory` cannot reach (ADR-014, superseding ADR-013). | Re-introducing a memory-side check reopens ADR-014 and adds an unreachable outbound dependency. |
| SA-PROV-01 | Recall provenance opt-in | `POST /v1/recall` accepts `include_provenance: bool` (default `false`). When `true`, each returned `RankedFact` with a source carries a `source: { origin_ref, modification_marker }` object; when `false` the field is omitted (lean response). | The agent needs the document handle + version token to check freshness itself; making it opt-in keeps the common response lean (SA-FRESH-01). | Field is additive and request-gated; a default-on flip only enlarges responses, never breaks parsing. |
| SA-AUDIT-01 | Audit trail storage | The audit trail is a per-tenant append-only SurrealDB table `audit_log` inside the tenant namespace, written synchronously on every authenticated call before the response is returned; it stores subject, operation, scope, outcome, token `jti`, correlation id, and timestamp — never the token, never fact content. | HLD 06/07 mandate a dedicated, append-only, per-tenant audit trail distinct from operational logs, erased with the tenant. | Moving the trail out of the namespace would break per-tenant erasure (ADR-011); kept in-namespace by design. |
| SA-RATE-01 | Rate limiting | A per-(subject, operation-class) **token-bucket** limiter: read class default 120 req/min burst 40; write class default 30 req/min burst 10; returns `429 RATE_LIMITED` with `RateLimit-Limit`/`RateLimit-Remaining`/`RateLimit-Reset` and `Retry-After`. | HLD 07 mandates agent-aware tiers with standard headers; token bucket gives smooth burst tolerance. | Limits are config; per-tenant overrides are a config map, not a contract change. |
| SA-MIG-01 | Migrations | Store schema evolves via numbered, ordered migration files applied through a `Migrator`; SurrealDB starts **schemaless** for `fact`/`entity`/`relationship` and tightens to **schemafull** as the model stabilises; every migration ships an explicit down path; applies to a shared store are a user action (dry-run first). | HLD 07 migrations stance + sql-safety layer rule (destructive changes surface rollback). | A missing down path blocks the migration at review; enforced by the Phase 4 Migrations spec. |
| SA-DELETE-01 | Verifiable deletion proof | A hard delete returns a `deletion_proof` = `{deleted_at, record_id, derived_removed: [...], embeddings_removed: N, digest}` where `digest` is a SHA-256 over the removed record ids; the operation is not reported complete until every derived summary and embedding is removed. | HLD 03/06 require verifiable deletion *including derived summaries and embeddings* with proof. | A partial delete must not report success; enforced by the Forget Gherkin error scenario. |
| SA-MAINT-CADENCE-01 | Maintenance cadence | The Maintenance Worker runs **idle-biased**: triggered after `idle_quiet_period` (default 300 s, `MEMORY_IDLE_QUIET_SECS`) with no writes for a tenant, with a hard fallback timer every `MEMORY_MAINT_MAX_INTERVAL_SECS` (default 6 h). Covers the worker's remaining duties — supersession, decay, re-embed (no consolidation; ADR-015). | A fallback timer guarantees progress under continuous load. | Cadence is config; affects maintenance freshness vs background cost, not correctness. |
| SA-LLMFREE-01 | No LLM dependency | `memory` holds no LLM dependency (ADR-015). The write path performs no LLM extraction; there is no server-side consolidation. The `LlmClient` port and `MEMORY_LLM_*` config are removed. Embedding + reranker (non-LLM inferences) are retained. | The agent already runs an LLM; extraction + synthesis are reasoning that belongs with the agent (ADR-015, completing ADR-014). | Re-introducing an LLM provider reopens ADR-015. |
| SA-WRITE-STRUCTURED-01 | Structured writes | `POST /v1/memories` `content` must be a **structured assertion object** (the agent extracts). The `agent_stated` flag is removed (all content is agent-asserted). An optional `memory_class` (default `episodic`, validated against the enum) lets the agent assert `semantic`/`consolidated` directly. | With LLM extraction gone, all content is agent-asserted structured data (SA-LLMFREE-01). | Field is request-gated and additive aside from the `agent_stated` removal; a write whose `content` is not an object is a validation error. |
| SA-VER-01 | API versioning | The HTTP surface is path-versioned under `/v1`; a breaking change takes `/v2`. The OpenAPI document at `/openapi.json` is generated from the handler types, not hand-maintained. | HLD 08 commits path versioning and a machine-readable contract for runtime codegen. | Hand-drift between code and contract is prevented by generation; a generation gap is caught by the Phase 4 API spec. |
| SA-SVC-01 | Shared service layer | The per-operation orchestration — authenticate→`ScopeContext` (C3), authorise the operation class, rate-limit (SA-RATE-01), idempotency (SA-IDEM-01), invoke the owning component, write the audit record (SA-AUDIT-01), and classify any failure to an X1 `code` — is a **transport-agnostic Service Layer (C9)** keyed on a verified `ScopeContext` and the existing 2C request/response DTOs, returning `Result<TypedResponse, AppError>`. Each edge (HTTP `C8`, MCP `C10`) is a thin adapter that maps its wire format to/from that layer; no orchestration logic is duplicated per edge (ADR-016). | The change request's core ask — "two manifestations of one service" — is exactly a demand that auth/scope/rate/idempotency/audit/error-classification exist once. Today they live inside the axum handlers (`EdgePipeline`); extracting them is what makes a second edge safe. | A second edge that re-implements any of these is a security/correctness hazard; the Phase 6 audit checks each concern has a single definition consumed by both edges. |
| SA-MCP-TRANSPORT-01 | MCP transport & identity (Option A) | The MCP edge runs as a networked service over **MCP streamable-HTTP**, carrying the same `Authorization: Bearer <OIDC JWT>` the REST edge validates; C3 (`Authenticator::validate`) is reused verbatim to derive the `ScopeContext`. No stdio/handshake/ambient identity model is introduced. | `memory` is a central, multi-tenant, OIDC-authenticated store; the per-agent-local component is the broker, not `recall`. A networked, bearer-authenticated edge fits its nature and reuses all governance unchanged (RFC 01, ADR-016). | A stdio/local-identity model reopens ADR-016 and would require a new auth seam, weakening AUTH1–AUTH7 + per-tenant isolation. |
| SA-MCP-TOOLS-01 | MCP tool surface | The MCP edge exposes **one tool per service operation** — `recall`, `remember`, `get`, `retire`, `delete` — plus native tool discovery (`tools/list`), the MCP analogue of `GET /v1` + `/openapi.json`. Tool input schemas are generated from the same 2C DTOs that back the OpenAPI document. Destructive `delete` is exposed but keeps the proof-gated hard-delete path (SA-DELETE-01) unchanged. | Operation parity across edges (RFC 01 desired behaviour #2); one schema source prevents REST/MCP contract drift. | Excluding an operation is a config decision, not a contract break; a schema source split would let the two edges drift, caught by the Phase 6 audit. |
| SA-MCP-MAP-01 | MCP result & error mapping | `remember`'s async-accepted (HTTP 202) outcome renders as the MCP tool's success output carrying the same idempotent acknowledgement the 202 body carries. An `AppError` renders as an MCP tool/protocol error **derived from the same X1 `code`** the HTTP edge maps to a status (SA-ENV-02 reused); the X1 registry is the single classification source. | Error/result parity across edges (RFC 01 #5) with no per-edge re-classification. | A per-edge error map would diverge; the Phase 6 audit asserts both edges derive from one X1 code via a table-driven test. |
| SA-BIN-01 | Two binaries, one core | The MCP server is a **separate binary** (`[[bin]]`, assumed name `memory-mcp`) built from the same crate, constructing its component state from the same `build_state` path and driving the Service Layer (C9). The existing `recall` (REST) binary's name, paths, status codes, envelopes, and headers are unchanged — the REST refactor is behaviour-preserving. | "Different manifestations of the same service" = two thin binaries over one core (RFC 01). Reusing `build_state` keeps configuration (X6) and observability (X3/X5) unified. | A forked config or a second copy of the wiring would diverge; the binary name is cosmetic (SA-BIN-01 note, OQ-NAME). |
| SA-TENPOP-01 | Consumer tenancy profile | A **consumer tenancy profile** is a deployment of the existing ADR-011 tenancy model at a tenant population of **10,000 and 50,000 namespaces**, each namespace holding exactly **one** end user (`teams = []`, one `user`). No tenancy mechanism changes: namespace-per-tenant with logical team/user scoping stands as written. | RFC 02-consumer-tenancy-profile reads the request as a deployment profile plus the operational work that makes it hold, not as a new tenancy model. ADR-011 is explicitly not reopened. | If the request is actually a new tenancy model, ADR-011 reopens and this pass is re-scoped; the benchmark numbers remain valid as a measurement of the current model. |
| SA-TENPOP-02 | Single-user tenancy is a retrieval requirement | At consumer scale a namespace holds one user **because** stage-1 vector search is KNN-then-filter with the over-fetch clamped to 1024 (`stage1_k` × 4, SA-RERANK-01): with thousands of unrelated users in one namespace the candidate window fills with other users' facts that then filter out, so a caller's own relevant facts may be absent from the final set. | Verified in `src/store/mod.rs` (KNN-then-filter with 4× over-fetch, clamp 1024) and restated in RFC 02-consumer-tenancy-profile *Verified context*. | If filter-first ANN were adopted the single-user namespace would become a preference rather than a requirement — a separate change with its own justification, out of scope here. |
| SA-BENCH-01 | Benchmark is a harness, not a runtime path | The many-namespace benchmark is a **separate binary** (`memory-bench`, C11) built from the same crate, driving the public `MemoryStore` trait and the `Migrator`. It adds no code to the `recall` or `memory-mcp` request paths and no runtime configuration to either binary. | Measuring the profile must not itself change what is measured; a separate binary keeps NFR-MA3 (single-binary story, ADR-009) intact because neither shipped binary grows. | If the harness had to live inside `memory`, the measured per-request cost would include harness overhead and the single-binary claim would need re-stating. |
| SA-BENCH-02 | Acceptance criteria 2 and 3 measure the **baseline** in this pass | Criteria 2 and 3 of RFC 02-consumer-tenancy-profile are written against the post-change system ("bounded by a configured batch"). In pass 1 the harness measures and reports the **current** unbatched sweep at both populations; the "bounded by a configured batch" form of both criteria is the exit criterion for pass 2 (the engineering), not for this pass. | The RFC's own handoff separates the benchmark (criteria 1–3, 7, 8) from the engineering (criteria 4–6, 10) and states the benchmark result decides how much engineering is warranted. A baseline measured before the change is what makes that decision possible. **Withdrawn January 2026 (RFC 03).** Criteria 2 and 3 were re-pointed by RFC 03: the measurements that decide the design are filter-first vs post-filtered relevance and latency across visible fractions, not the unbatched sweep at two populations. | If criteria 2 and 3 were meant to gate pass 1 on the batching work existing, pass 1 and pass 2 are not separable and the whole profile must be specified as one unit. |
| SA-FOOTPRINT-01 | Per-namespace footprint definition | The **per-namespace footprint** reported by the harness is the triple (`object_count`, `steady_state_bytes`, `provision_millis`). `object_count` is the sum of tables, indexes, field definitions, analyzers and the `schema_migrations` bookkeeping row defined within one tenant namespace, read back from `INFO FOR DB` after migration. `steady_state_bytes` is the on-disk delta attributable to one freshly-provisioned, zero-fact namespace, measured as (total store size after N namespaces − total store size after 0 namespaces) ÷ N. `provision_millis` is wall-clock for one `Migrator::migrate_up` against a never-seen tenant. | Acceptance criterion 1 requires objects, steady-state bytes and wall-clock per namespace; each needs one unambiguous definition or the numbers are not comparable between runs. **Withdrawn January 2026 (RFC 03).** The per-namespace footprint leg was **withdrawn by RFC 03** and no code implements it; `provision` and `footprint` exist in no binary. The definition stands so that a reader of the term, and the specs that cite this id, still resolve — reviving the leg means re-deriving it against C11's current report shape, not restoring the text. | A different byte-attribution method (per-namespace file accounting rather than a division) changes the absolute figure; the division is stated so a later run can reproduce it. |
| SA-SWEEP-COST-01 | Per-tick cost attribution | The harness attributes scheduler per-tick cost to three measured parts: (a) the single `list_tenants()` call, which issues `INFO FOR ROOT` and returns **every** defined namespace in one response; (b) the per-tenant `tenant_is_due` probe, which issues `scan_recent_episodes(ctx, since, limit = 1)`; and (c) the per-tenant `ensure_and_use` preamble, which runs `DEFINE NAMESPACE IF NOT EXISTS` + `USE NS` + `DEFINE DATABASE IF NOT EXISTS` + the `schema_migrations` DDL + `SELECT version FROM schema_migrations` on **every** store call, including read-path calls. | All three are verified in source: `INFO FOR ROOT` in `src/store/mod.rs:765`; the per-tenant loop in `src/maintenance/mod.rs`; `select_namespace` + `current_version` reached from `ensure_and_use` on 24 store methods in `src/store/mod.rs`. Reporting one aggregate tick figure would hide which of the three dominates, and they have different fixes. **Withdrawn January 2026 (RFC 03).** The sweep leg was **withdrawn by RFC 03**, which calls the sweep problem absent at ten namespaces; `sweep` exists in no binary. The attribution stands as the definition of the cost, not as a description of an instrument that measures it. | If the three are not measured separately, the pass-2 engineering could batch the sweep (part b) while leaving the per-operation preamble (part c) — which also sits on the read path and therefore on NFR-P2 — untouched. |
| SA-FOOTPRINT-02 | Object count derives from the migration set | The harness derives the expected per-namespace object inventory by counting `DEFINE TABLE` / `DEFINE INDEX` / `DEFINE FIELD` / `DEFINE ANALYZER` statements in the migration set it applied, and uses `INFO FOR DB` only as a cross-check that logs a divergence. | The counts are verifiable here — `migrations/0001_init.up.surql` carries exactly 10 tables, 19 indexes, 80 field definitions and 1 analyzer, with the HNSW vector index `fact_hnsw` at line 46. `INFO FOR DB` is read nowhere in `src/` or `tests/`, so its response-key names cannot be verified and must not sit on the critical path (identifier-verification layer rule). **Withdrawn January 2026 (RFC 03).** Withdrawn with the footprint leg (RFC 03); no code derives an object inventory. | If the engine reports a different inventory than the migration set implies, the cross-check logs the divergence and the migration-derived figure is reported; the discrepancy is then a C1 defect rather than a harness defect. |
| SA-BENCH-RENDER-01 | `render_up` widens to `pub(crate)` | `Migrator::render_up` is private (`fn render_up`, `src/store/migrate.rs:167`). The database-per-tenant benchmark leg needs the rendered migration statements, so this work widens it to `pub(crate)`; `src/bench` is in the same crate. | Re-reading `migrations/0001_init.up.surql` in the harness would duplicate the `<dim>` substitution `render_up` performs and would drift the moment the migration set grows. Widening one function to crate visibility is the smaller change and keeps a single renderer. | Widening beyond `pub(crate)` would enlarge C1's public surface against rule C12 (minimise public surface); `pub(crate)` is the narrowest visibility that reaches `src/bench`. |
| SA-BENCH-ISOLATION-02 | Pre-flight prefix guard | Before provisioning, the harness calls `list_tenants()` once and refuses to run when any existing namespace id begins with `MEMORY_BENCH_TENANT_PREFIX`, exiting 2 without creating or dropping anything. | `DEFINE NAMESPACE IF NOT EXISTS` adopts a colliding pre-existing namespace; teardown's prefix check would then pass and drop it. One `INFO FOR ROOT` at start-up makes the adoption impossible, which is cheaper than a per-namespace ownership marker. | A benchmark re-run against a retained population (`MEMORY_BENCH_RETAIN=true`) is refused and needs the prior population dropped first, or a different prefix — friction accepted in exchange for the guarantee. |
| SA-AUTHZ-01 | Write authority by fact class | A `remember` request may carry an optional `fact_class` string that names, in the **caller's** vocabulary, the class of assertion being made. A token may carry an optional `memory_fact_authority` claim listing the classes it is entitled to assert and, per entry, the single source it may attribute them to. The comparison is between two opaque strings: `memory` holds no class vocabulary and derives no meaning from either side (ADR-019, SA-LLMFREE-01). The check runs in **exactly one place** — C9's `remember` chain, after authorisation and before the `ExtractFact` job is enqueued — so both the HTTP edge (C8) and the MCP edge (C10) inherit it without a second copy (SA-SVC-01). | ADR-007 in the Companion Platform's corpus places this control in `memory` so that it lives in one testable place rather than in each caller. Placing it after `begin` rather than inside it is what puts the refusal on the `finish_error` path, which audits; a fourth `Op` variant would refuse correctly and leave no trail (SA-AUTHZ-04). Placing it after body deserialisation is what makes the `fact_class` field readable. | A caller that omits `fact_class` is asserting nothing classed and is admitted on `memory.write` alone, so a principal determined to evade the control writes the same content unlabelled. That is the boundary of a label-based control and is stated rather than hidden: the protection a consumer gets is that a fact it *reads back* as class `A` was written by a principal entitled to assert `A`. Closing the unlabelled route would require `recall` to infer class from content, which SA-LLMFREE-01 and the RFC's out-of-scope list both forbid. **A second, sharper limit was found during implementation and is RFC 04 open question 8:** the authorised label is *discarded* after the decision — it is not carried into the enqueued job and `Fact` has no class field — so a consumer cannot read back the label that was authorised, only whatever the caller placed inside `content`, which `memory` never compared against `fact_class`. Until the class is stored, the guarantee this control delivers is "the write was authorised", not "the fact you are reading was authorised as this class". |
| SA-AUTHZ-02 | Absent authority claim | A validated token carrying **no** `memory_fact_authority` claim may assert every class, exactly as every token may today. The absence is observable rather than silent: C3 logs the authority claim name it reads at start-up, and C9 increments `memory_write_authority_absent_total` on every write admitted only because the token carried no claim. | The compatibility decision, settled January 2026. Defaulting to no authority would be safe and would stop every current caller on upgrade, breaking RFC 04 acceptance criterion 5. A silent safe default and a silent unsafe default fail the same way, so the chosen answer takes the compatible default and pays for it with a signal a deployment can alarm on. | A deployment that believes the control is in force when no token carries a claim is protected only by the counter; if the counter is not alerted on, the control is absent and nothing says so. The counter, not the default, is the mitigation. |
| SA-AUTHZ-07 | Class authority governs assertion only | Holding — or lacking — authority over class `A` has no effect on `POST /v1/memories/{id}/retire` or `DELETE /v1/memories/{id}`. Those two operations continue to be governed by `Op::Forget` plus C1's ownership check, unchanged. | Settles RFC 04 open question 4 deliberately rather than letting it emerge from where the check sits. Retire and delete assert nothing — they name an existing record by id — so there is no class label on the request to compare. Deriving the class from the *stored* fact would mean reading the record before authorising it, which turns a `404 NOT_FOUND` into a signal that the record exists and is of a class the caller may not touch, breaking RFC 04 acceptance criterion 3. | A principal entitled to assert class `A` and holding `memory.forget` can retire any fact it owns regardless of class. Since it can only reach facts inside its own scope, and could equally have retired them before this change, the control's blast radius is unchanged. |
| SA-AUTHZ-09 | The authorised class is the stored class | The `fact_class` the Service Layer authorises is carried into the `ExtractFact` job payload and persisted on the resulting `Fact` (and on a `QuarantineRecord`, when the trust gate holds the write mid-band). It is returned on every read that returns the fact. `memory` stores and returns an opaque string: it validates it against no list, derives no meaning from it, and treats no value specially. `Fact.fact_class` is `Option<String>` with `#[serde(default)]`, so a row written before the field decodes with `None`. | Without it, the label the write gate judged and the label a consumer acts on are different strings with nothing keeping them in step (RFC 05). `memory` never inspects `content` to decide what a fact is (SA-LLMFREE-01), so a caller can be authorised for one class while its own readers see another inside `content`. Storing the judged label is what makes SA-AUTHZ-01's decision observable to the reader it is supposed to protect. | The field is stored but **not filterable** — `RecallFilters` does not gain it, so a consumer needing server-side selection by class at a corpus size where client-side filtering stops working has a further change to make: an index on the fact table plus a stage-1 query predicate, against the NFR-P2 read budget. That is deliberately deferred until a consumer measures the need. |
| SA-AUTHZ-10 | A superseding fact carries its own class | When a write supersedes an existing fact, the successor's `fact_class` is the class of the **write that created it**, never inherited from its predecessor. A supersession is a new assertion that passed the gate with its own token; inheriting would attach a label no gate judged for that write. | Stated rather than left to emerge from wherever the supersession code happens to copy fields from. The failure it prevents is a token authorised for nothing at all superseding a `medication-authoritative` fact and the successor silently keeping that class. | If a caller genuinely wants the successor to carry the predecessor's class, it sends that class on the superseding write and is authorised for it — which is the same check, applied to the assertion actually being made. |
| SA-BENCH-ISOLATION-01 | Benchmark runs against a disposable store | Every harness run targets a store instance it provisions and drops itself, selected by `MEMORY_BENCH_STORE_URL`; it never targets a store holding real tenant data, and it refuses to start when `MEMORY_BENCH_STORE_URL` is unset. | The harness creates and drops tens of thousands of namespaces; pointed at a live store that is destructive. Requiring an explicit dedicated endpoint makes the blast radius a deliberate choice. | Without the guard a mistyped endpoint drops production namespaces; the refusal-to-start check is the mitigation and is asserted by a Gherkin scenario. |
| SA-COLL-01 | Collection label | A fact, entity, relationship and source may carry a `collection` matching `^[a-z0-9:_-]{0,64}$`; `""` is the default collection, held by every row written before migration `0007` and by every write naming none. `memory` never interprets the label. | ordin needs one set per team folder inside one scope; a label is the smallest change that keeps the read filter as the only access rule. | A richer label would need a vocabulary `memory` does not own. |
| SA-COLL-02 | Collections in play | Without `filters.collections`, stage-1 runs every signal for each collection present among the caller's readable facts; with it, for exactly the listed ones (1–32). | SA-COLL-03 | Vector strategy per collection | With more than one collection in play, or a collection filter, each collection's vector run is `FilterFirstExact` within that collection; a single-collection unfiltered recall keeps `VectorStrategy::for_profile`. | KNN-then-filter starves a small collection (the clamp to 1,024). | A very large collection pays O(V) per recall. |
| SA-COLL-04 | Fusion constants | Reciprocal rank fusion with `k = 60`; bonus 0.05 for rank 1 in any run, 0.02 for rank 2–3; per-collection quota `q = max(1, ⌊stage1_k / (2 × n)⌋`, `n` the number of collections with candidates); `fused_norm = fused / fused_max`. | qmd's published constants; the quota guarantees each collection's best matches reach the reranker. | Different constants change which candidates reach rerank, not the reranked order. |
| SA-COLL-05 | SQL storage parity | ordin's SQL storage (change M-2) applies the same runs, fusion and erasure; its DDL is owned by ordin's Memory Service spec. | One behaviour on every backend (ADR-101 of the ordin HLD). | Divergence between backends would make ordin's results differ from the benchmark's. |
| SA-SUBQ-01 | Typed sub-queries | A recall carries exactly one of a non-empty `query` and 1–4 `searches`, each `{type, query}` (type `lex` or `vec`, query 1–4,096 characters). | The agent writes each phrasing for the signal it suits; ADR-012's model rewording stays off. | — |
| SA-SUBQ-02 | Sub-query weights | The first sub-query's runs weigh 2.0, every other 1.0. | The first is the agent's main intent. | A different weight shifts candidate selection only. |
| SA-SUBQ-03 | Rerank query | The rerank query is the plain query, or the first sub-query's text; one rerank call per recall. | One rerank fits the 60 ms sub-budget. | Reranking against a keyword phrase may score meaning matches lower. |
